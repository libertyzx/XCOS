### A1（可复现的丢唤醒）通知计数满判定在 `uint8_t` 回绕处失效

**状态**：✅ **已修复**（2026-09-14）——见 [`Docs/问题跟踪/修正方案/20260914_通知待处理标志/修正方案.md`](../修正方案/20260914_通知待处理标志/修正方案.md)（仿真 A/B 对照：旧代码 2 项失败 / 新代码 0 失败）

**证据**
```c
/* XC_Task.c:550  非等待分支 */
if((phTCB->NotifyProduced + 1U) != phTCB->NotifyConsumed) { phTCB->NotifyProduced++; }
/* XC_Task.c:559  等待+锁窗口分支 */
if((phTCB->NotifyProduced + 1U) != phTCB->NotifyConsumed) { phTCB->NotifyProduced++; }
/* XC_Task.c:562  事件计数同款 */
if((phXCOS->EventProduced + 1U) != phXCOS->EventConsumed) { phXCOS->EventProduced++; }
```

**机理**：`NotifyProduced/Consumed` 是 `uint8_t`，表达式中被**整型提升为 `int`**，于是"留一格判满"所需的模 256 语义丢失：

* 设计意图：`(Produced + 1) mod 256 == Consumed` ⇒ 满（丢弃本次）；
* 实际计算：`Produced == 255, Consumed == 0` 时得 `255 + 1U = 256`（**未取模**）⇒ `256 != 0` **成立** ⇒ 误判"未满" ⇒ 自增 ⇒ **`Produced` 回绕成 `0 == Consumed`** ⇒ "有通知"变成"没有通知"。

**触发条件（关键，易误述；经 2026-09-14 仿真实测修正）**：失效需要**同时**满足两条 ——

1. **判满误判**：`P == 255` 时 `P + 1U` 提升为 `int` 得 `256`，与任何 `C ∈ 0..255` 都**不相等** ⇒ 误判"未满" ⇒ 自增 ⇒ `P` 回绕成 `0`。注意：**只有当 `C == 0` 时**回绕才导致 `P == C`（记录被抹）；`C ≠ 0` 时回绕前后的**差值不变**（仍是"满"），**无可观测影响**；
2. **未消费量恰为 256 的整数倍**（≥256）：回绕抹掉记录后，**后续任何一次发送都会把差值重新变成非零** ⇒ 只有恰好在"未消费量 ≡ 0 (mod 256)"的时刻做检查，才会看到"没有通知"。

⇒ 即：`Consumed == 0`（上一次消费者同步时生产者恰为 0；新注册/复位后的任务天然满足）**且** 自那以后未被消费的发送次数 ≡ 0 (mod 256)。决定因素是"**消费者多久不消费 + 计数落点**"，而非"发送总量"。
> **实测对照**（§6.2）：300 次发送（300 mod 256 = 44）**旧代码不失败**；**256 / 512 次旧代码失败**（仿真输出 `r3 = 0 / r4 = 0`），新代码全部通过。

**逐站点可达性与失效形态（本轮通读全部代码复核）**

| 站点            | 上下文                  | 未消费量能否到 255                                                                                                                                                                                       | 失效形态                                                                                                                                                  |
| --------------- | ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `XC_Task.c:550` | 非等待分支（任务/中断） | **能**（需命中 `Consumed==0` 且未消费量 ≡0 mod 256）：消费者=目标任务自身，只有它 `WaitNotify`/`ClrNotify`/`Reset` 才使差值归零                                                                         | **一次性抹掉全部 255 条记录** ⇒ 该次 `WaitNotify` 本应"提前通知"立即返回却阻塞；若此后无新发送 ⇒ `WaitNotify(0)` **永久阻塞**、`WaitNotify(N)` 超时返回 |
| `XC_Task.c:559` | 等待 + 锁窗口（仅中断） | **能**（同上，且此刻任务正在 `WAIT`）                                                                                                                                                                    | **唯一唤醒凭据被抹**：`XC_Sch.c:187` 的 `Produced != Consumed` 为假 ⇒ 事件扫描**跑到了也扫不醒它** ⇒ `WaitNotify(0)` **永久睡眠**（最严重形态）         |
| `XC_Task.c:562` | 事件计数（仅中断）      | **不能**：消费者=主循环，每轮 drain（`XC_Sch.c:292-294`，`Trigger = EventProduced`）⇒ 未消费量 = "**一轮主循环内命中锁窗口的次数**"（0~几次）；要到 255 需"单轮内命中锁窗口 255 次" ⇒ **工程上不可达** | 同批修（零成本、写法一致性），**不构成实际风险**                                                                                                          |

**影响**：站点 550/559 表现为**偶发丢一次唤醒 / 偶发永久阻塞**（取决于该任务此后是否还能收到新通知）；触发需同时命中"`Consumed==0` 且未消费量 ≡0 mod 256"（约 1/256 量级），现场极难复现定位；站点 562 仅理论。

**方案（最小）**：比较前按 `uint8_t` 截断，保住"留一格"的本意（满则丢弃，不再回绕）：
```c
if((uint8_t)(phTCB->NotifyProduced + 1U) != phTCB->NotifyConsumed) { phTCB->NotifyProduced++; }
if((uint8_t)(phXCOS->EventProduced + 1U) != phXCOS->EventConsumed) { phXCOS->EventProduced++; }
```
**方案（更彻底）**：把"计数对"换成**单标志** `NotifyPending`（生产侧只写 1、消费侧写 0，天然无读改写），顺带省 1 字节、消掉整类问题。

**方案（若必须保留"计数"能力：差值法——这才是双计数的正确写法）**：
```c
/* 未消费量 = (uint8_t)(P - C) —— 模 256 差值,天生无回绕边界 */
if((uint8_t)(phTCB->NotifyProduced - phTCB->NotifyConsumed) < 255U) { phTCB->NotifyProduced++; }
```
* `P - C` 在 `int` 中算出（范围 −255..255），**截断成 `uint8_t` 后正是"模 256 的未消费量"** ⇒ 不需要"留一格"的巧合，也不存在回绕；
* 对 **N 槽队列**同样成立：`if((uint8_t)(P - C) < N) { ... }`（把 `255U` 换成槽数）—— 即 Linux `kfifo` / `CIRC_SPACE` 的惯用法；
* 代价：生产侧仍是"读 + 减 + 比较 + 分支 + 写"（5~6 条、跨读），比单标志贵。

**"安全度"排序（判据：前提能否强制 + 失效能否检测 + 边界多少）**

| 排序  | 模型                                   | 并发路径                     | 内在边界                | 失效可检测性                                                          | 适用场景                                    |
| ----- | -------------------------------------- | ---------------------------- | ----------------------- | --------------------------------------------------------------------- | ------------------------------------------- |
| **1** | **单标志**                             | 1 条 `store`，**无任何判断** | 无                      | 违反纪律（`\|=`/位域）可由脚本/评审抓；其余失效良性（多一次立即返回） | **单槽"有没有"**（XCOS 通知的语义）         |
| 2     | **差值法双计数**                       | 读+减+比较+分支+写           | 无（差值法无回绕）      | 依赖"单写者"约定（**用户可违反**，框架无法强制）                      | **多槽队列**（需要"还剩几格/有几条待处理"） |
| 3     | 留一格判满 **+ 必须 `(uint8_t)` 截断** | 同上                         | 有（满则丢弃=设计行为） | 同上；且整型提升陷阱仍在（`(uint8_t)` 易被后继修改者"顺手简化"掉）    | 只求最小改动的存量代码                      |
| 4     | **现状（留一格 + 未截断）**            | 同上                         | **有缺陷**              | **低**：静默、1/255 概率、依赖时序                                    | 不可接受                                    |

> **要点**：双计数**不是**"冗余备份"——两个计数不是同一信息的两个副本，而是"差值"的两半，因此**没有投票/纠错能力**：任一被写坏或读到旧值，得到的就是**错误决策**，且无法自检。它的"稳"来自"每字段单写者"这条**不可强制**的约定；把"单槽布尔"做成"带边界的计数"，反而引入了唯一那条**静默**失效路径。⇒ **模型匹配需求**才最安全：单槽用单标志，多槽用差值法。

**验证**：`WaitNotify` 前连续发 300 次通知 ⇒ 断言"等待立即返回且不超时"；或单测里把 `Produced` 直接置 255 再发一次，检查 `Produced != Consumed` 仍成立。

## 附录 A：A1 的"彻底方案"——通知计数对 → 单标志（详细设计）

### A.1 现状为什么用"生产/消费计数对"（设计初衷）

框架不做关中断、不做原子 RMW、不加平台原语，因此"中断↔主循环"共享状态必须满足 **SPSC 三约束**：

| #   | 约束                            | 现状如何满足                                                                            |
| --- | ------------------------------- | --------------------------------------------------------------------------------------- |
| 1   | **每个可写变量只有一个写者**    | `NotifyProduced` 只有生产者（发送侧）写；`NotifyConsumed` 只有消费者（等待侧）写        |
| 2   | **写是原子宽度**（单字节对齐）  | 两者都是 `volatile uint8_t` ⇒ Cortex-M 单字节存取天然原子                              |
| 3   | **不做跨上下文的读改写（RMW）** | 生产者只 `++Produced`（唯一写者，RMW 安全）；消费者只 `Consumed = Produced`（唯一写者） |

**代价**：为实现"计数器"引入了跨读（生产者要读 `Consumed` 判满、消费者要读 `Produced` 判有无）与"满则丢弃"的判满分支 ⇒ 才有 A1 的 `uint8_t` 回绕混叠。

### A.2 为什么"单标志"同样满足 SPSC（且更强）

单标志的设计是：**生产侧只写常量 `1`、消费侧只写常量 `0`**：

```c
/* 生产者(发送侧, 任务或中断) */   phTCB->pNotifyData = d;  phTCB->NotifyPending = 1U;
/* 消费者(等待侧/唤醒侧)      */   if (phTCB->NotifyPending) { phTCB->NotifyPending = 0U; ... }
```

它**不是**"两个写者写同一个变量的经典错误"，因为两个写者的**写集合互斥**（生产者只会写 `1`，消费者只会写 `0`），字节写是原子的，所以任一交错的结果只会是 `0` 或 `1`，**不存在"丢失信息"的中间态**（不像 `++` 那样有"读-改-写"的丢更新）。逐条对照：

| 关注点                             | 计数对（现状）                                                  | 单标志（方案）                                                   |
| ---------------------------------- | --------------------------------------------------------------- | ---------------------------------------------------------------- |
| 每个字节的写者数                   | 1 个（每字段）                                                  | 2 个，但**各写常量**（{1} 与 {0} 互斥）                          |
| 是否需要 RMW                       | 需要（`Produced++`）                                            | **不需要**（常量 store）                                         |
| 跨读                               | 有（读对方字段做判断，可能读到旧值）                            | **无**                                                           |
| 回绕混叠                           | ❌ 255 处混叠（=A1）                                            | ✅ 无（布尔）                                                    |
| 多生产者（同任务两个中断都发通知） | ❌ 两个 `Produced++` RMW 竞争 ⇒ 丢更新（文档要求用户加锁）     | ✅ 写同值 `1` ⇒ **幂等**（数据指针 `pNotifyData` 仍需用户保证） |
| 语义能力                           | 可计数（但**没有任何 API 暴露计数**，`ClrNotify` 也只是"全清"） | 布尔（与全部已文档化行为等价）                                   |
| 占用                               | 2 字节                                                          | 1 字节（TCB 仍 **44B**，差值落进原有对齐 padding）               |
| ISR 路径                           | `load Produced / add / cmp Consumed / branch / store`           | **单条 `store`**                                                 |

### A.3 "不会丢唤醒"的三类交错论证

设消费者侧时序为：**[1] 置 `NotifyState = WAIT` → [2] 读 `NotifyPending` → [3a] 命中则消费（置 0）并保持 READY，[3b] 未命中则 `BLOCKED` + 入表**（这三点必须按此顺序，与现状一致）。

| 交错情形                                       | 结果                                                                                                                                                                  | 是否丢唤醒                                        |
| ---------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| 生产者的 `NotifyPending = 1` 落在 **[1] 之前** | [2] 读到 `1` ⇒ 不阻塞、立即消费                                                                                                                                      | ✅ 不丢                                           |
| 落在 **[1] 与 [2] 之间**                       | 同上（[2] 读到 1）                                                                                                                                                    | ✅ 不丢                                           |
| 落在 **[2] 与 [3b] 之间**                      | 生产者看到 `NotifyState == WAIT` ⇒ 走**唤醒路径**（锁窗口内=登记异步；否则直接搬表）；主循环随即把它从表里搬回就绪表                                                 | ✅ 不丢（与现状同机制）                           |
| 落在 **消费者 [3a] 置 0 之后**                 | 标志保持 `1` ⇒ 该任务下次 `WaitNotify` 立即返回（"提前通知"语义）                                                                                                    | ✅ 不丢（仅"多一次不阻塞"，良性；现状计数对同理） |
| 消费者置 0 与生产者置 1 **同时**（同一字节）   | 结果非 0 即 1：<br>· 若 `1` 胜 ⇒ 标志保留 ⇒ 下次等待立即返回（良性）<br>· 若 `0` 胜 ⇒ 消费方**正处于"唤醒该任务"的路径上**（任务会运行并读到最新 `pNotifyData`） | ✅ 不丢                                           |

> 关键点：**"置 0 的只有正在消费/正在唤醒该任务的那一方"**，所以"清掉一次通知"永远伴随"任务即将运行（或继续运行）"，不会出现"清掉了但没人跑"的丢唤醒。

```c
   (XC_LIST_TO_TCB(pIterator)->NotifyPending != 0U) &&
   (XC_LIST_TO_TCB(pIterator)->TaskState != (uint8_t)XC_TASK_SUSPEND)) {   /* A2 一并修 */
    XC_LIST_TO_TCB(pIterator)->NotifyPending = 0U;
    ...MoveToReadyList + NotifyState=WAKEUP + TaskState=READY...
}
```

### A.5 语义等价性与收益

| 已文档化行为                     | 计数对                   | 单标志                     | 是否等价        |
| -------------------------------- | ------------------------ | -------------------------- | --------------- |
| 提前通知（先发后等）             | 等待不阻塞               | 等待不阻塞                 | ✅              |
| 等待中被通知                     | 唤醒                     | 唤醒                       | ✅              |
| 多次发送后消费                   | 一次消费清空全部         | 置 1 幂等，一次消费清空    | ✅              |
| `ClrNotify`（丢弃历史通知）      | `Consumed = Produced`    | `NotifyPending = 0`        | ✅              |
| `Reset/Remove/Reg`               | 清空计数                 | 清标志                     | ✅              |
| `IsNotifyTimeout()`              | 由 `NotifyState` 决定    | 同                         | ✅              |
| 满则丢弃（>=255 次未消费）       | 有该分支，且回绕时有 bug | "丢弃"语义等价（重复置 1） | ✅（且无 bug）  |
| 未消费通知的**计数**（可读数量） | 存在但无 API 暴露        | 不存在                     | ✅ 对用户不可见 |

**收益**
* **A1 整类缺陷消失**（回绕混叠在布尔模型下不存在）；
* ISR 路径少 2 次读 + 1 次比较 + 1 次分支（预期 **5~10 周期/次**；`SendNotify` 非等待分支在实测中从 63 → 54 属同类变化的量级）；
* 多生产者场景从"❌ 需加锁"变为"**✅ 写同值幂等**"（数据指针仍需用户保证）；
* TCB **不倒增**（44B，差值进 padding），并空出 1 字节 padding 可用于将来 `PendAction`；
* 代码/文档更易解释（"有没有待处理"一个布尔即可）。

### A.6 必须遵守的纪律（否则会退化成错误实现）

1. **只允许常量写**：`NotifyPending = 1U` / `= 0U`；**严禁** `|= 1U`、`++`、`&=` 等 RMW 形式；
2. 字段必须 `volatile`（防编译器缓存/重排）；
3. **数据先写、标志后置**（保证消费侧"看到标志即看到最新 `pNotifyData`"）；
4. 消费者侧顺序不可变：**先置 `WAIT`、再查标志**（这是"不丢唤醒"的核心，见 A.3）；
5. 生产侧仍须满足 **单任务单生产者**（对"落表"而言；标志本身已放宽，但 `pNotifyData` 与将来的登记机制仍按 SPSC）；
6. 若 CPU 存在内存重排序，仍需与现状相同的屏障约定（文档已有说明）。
7. **平台前提（与现状相同，非本方案新增）**：目标平台必须保证**对齐的单字节 `volatile` 存取是"整体写入"的**——不会被撕裂，也不会与相邻字节合并成"读-改-写"。
   * 现状**已经**依赖同一前提：两个计数就存放在 TCB 偏移 **34/35 的相邻字节**上，`NotifyProduced++` 若被实现为"字读取-改-写"，就会把 `NotifyConsumed` 一起改坏（= 更低级的缺陷）；Cortex-M 上是 `LDRB/STRB`、8 位机上是单字节指令，均满足。
   * 本方案**不**要求任何"原子读-改-写"（无 `++`/`|=` ⇒ **没有 RMW**），也**不**要求两次 store（生产侧置 1 / 消费侧置 0）之间的原子性或顺序性：任一交错的结果只可能是 `0` 或 `1`，协议对两者都安全（见 A.3）。
   * **实测（本仓库工具链，2026-09-14）**：`NotifyPending = 1U/0U` 在 **AC5 V5.06u7**（`-O1` / `-O3` / `-Ospace`）与 **armclang/AC6**（`-O2`，Cortex-M3）下**都只生成一条内存访问**：
     `MOVS r1,#1` + `STRB r1,[r0,#0]`（`MOVS` 仅装载常量、不访问内存；`STRB` 是**唯一**的存储 ⇒ 内存层面不存在"被中断在中间"的中间态）。
     对照（同一探针程序）：现状 `NotifyProduced++` = `LDRB`+`ADDS`+`STRB`（**3 条 RMW，可被中断在"改"与"写"之间**，靠"单写者"约定才安全）；位域/`|=` 写法 = `LDRB`+`ORR`+`STRB`（读-改-写，**会波及同一存储单元内的其它位**）⇒ 这正是规则 1 禁止 `|=`、禁止用位域承载标志的原因。
   * 另：现状工程的反汇编（`Examples/CortexM3_Test/Debug/Listings/xc_task.txt:804-845`）证实计数确实按**字节**访问（`LDRB/STRB` 于 TCB 偏移 `0x22/0x23`），**同时验证了本文的偏移表**（`0x20`=TaskState、`0x21`=NotifyState、`0x22/0x23`= 计数对）。
   * **平台矩阵（本框架可能落地的目标：`uint8_t` 写 0/1 是否"单条指令 + 对该字节原子"）**

     | 平台                                    | 字节写指令                            | 单条指令 | 对该字节原子                                                      | 需要留意的坑                                                                             |
     | --------------------------------------- | ------------------------------------- | -------- | ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
     | ARM Cortex-M0/M0+/M3/M4/M7（v6-M/v7-M） | `STRB`                                | ✅       | ✅                                                                | 无（TCB 在 Normal SRAM；Device 区另有访问属性约定）                                      |
     | ARM Cortex-A/R、AArch64（v7-A/v8-A）    | `STRB`                                | ✅       | ✅                                                                | 弱序模型：**跨核**需 release/acquire；同核（主循环+中断）程序序即够                      |
     | x86 / x86-64                            | `MOV byte ptr [m], imm8`              | ✅       | ✅（Intel SDM：单字节访问原子）                                   | TSO ⇒ store-store 有序，硬件层面自动满足"数据先写、标志后置"                            |
     | RISC-V（RV32I/RV64I/RV64GC）            | `SB`                                  | ✅       | ✅（基规范/RVWMO：自然对齐且 ≤8B 的访问单拷贝原子，受 PMA 约束） | 个别核无字节使能 ⇒ 见下方 C 类                                                          |
     | 8051                                    | `MOV direct,@Rn`、`MOV @Ri,A`         | ✅       | ✅（中断只在指令边界采样）                                        | 位寻址区可直接 `SETB/CLR`（更优）；对 P0~P3 的位操作是端口层 RMW，与 RAM 标志无关        |
     | AVR（AVR8）/ MSP430                     | `ST/STS`、`MOV.B`                     | ✅       | ✅                                                                | `SBI/CBI`（I/O 区位操作）是 RMW 且可被中断——但那是 I/O 寄存器，不是 RAM 标志           |
     | PIC 8/16/32                             | `MOVWF/MOVFF`                         | ✅       | ✅                                                                | 位域会退化成读-改-写；`BSF/BCF` 对**端口**寄存器读引脚（经典 RMW 陷阱），与 RAM 标志无关 |
     | 16 位字寻址 DSP（C28x/SHARC 等）        | `uint8_t` 可能不存在（`CHAR_BIT!=8`） | ⚠️     | ⚠️                                                              | 见下方 B 类：改用机器字标志（规则 8）                                                    |

   * **三类"会出问题"的例外（与平台无关的共性）**：
     * **A 类｜同一存储单元被多个对象共享**：位域、`__packed` 子字字段 ⇒ 编译器生成"读-改-写"，可被中断在中间，且**会连带改写同单元的其它位**。⇒ 规则 1 禁止 `|=`、禁止位域承载标志。
     * **B 类｜最小可寻址单位不是 8 位**：`CHAR_BIT != 8`（C28x/SHARC 等）⇒ `uint8_t` 可能未定义；用规则 8 的类型旋钮（独占机器字）。
     * **C 类｜存储/总线层 RMW + 其它总线主机并发**：SDRAM（无字节掩码）、带 ECC 的 SRAM 等在控制器内部做读-改-写；若另有 **DMA 同时写同一字**，可能出现"字节写回写坏邻字节"。⇒ 让标志独占一个字，或约定 DMA 不触碰 TCB。
   * **关键对照**：A/C 两类对**现状计数对同样成立，而且更严重**——`NotifyProduced++` 本身就是 3 条指令的 RMW（在"仅字访问原子"的平台上必然被中断在中间）；单标志的唯一内存访问是一条 store ⇒ 在弱平台上**比现状更鲁棒**。
8. **若目标平台仅"字访问"原子（如部分 DSP/8 位机外扩总线）**：把标志类型提升为机器字即可 —— 预留 `XC_CFG_NOTIFY_FLAG_TYPE`（默认 `uint8_t`，可配 `uint32_t`），代码不变，RAM +3B（可直接吃掉预留 padding）。**注意**：此调整对现状计数对同样必要，所以它不是"单标志引入的额外代价"。
9. **多生产者方面本方案要求更低**：两个中断都写同值 `1` 是**幂等**的（现状是两个 `Produced++` = 丢更新的 RMW ⇒ 必须用户加锁）；但 `pNotifyData` 的并发写仍由用户保证（框架无法代为解决）。

### A.8 专题：在"等待通知的处理"过程中发生"发送通知"，会有问题吗？

**先分谁可能与 `XC_Task_HandleWaitNotify` 并发**：XCOS 是协作式、非抢占 ⇒ **任务上下文的发送不可能与它并发**（同一线程），唯一能"插进来"的是**中断**。

#### A.8.1 中断发送：按时间窗逐一分析（现状实现）

`HandleWaitNotify` 的时序：**[L] 加锁 → [1] 置 `WAIT` → [2] 查是否有通知 → [3a] 有则消费（清计数）保持 READY / [3b] 无则置 `BLOCKED` + `HandleBlocking` 入表（内部解锁）→ [U] 解锁**。

| 窗口                         | 中断看到的状态     | 中断走的路径                                         | 结果                                                                 | 现状是否安全                                                                    |
| ---------------------------- | ------------------ | ---------------------------------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| [L] 之前                     | 非 `WAIT`          | 只记录（`Produced++`）                               | 消费者 [2] 读到 ⇒ 不阻塞                                            | ✅ 安全（"先置 WAIT 再查"的核心作用）                                           |
| [1]~[2] 之间                 | `WAIT` + `Lock==1` | 异步（`Produced++` + `EventProduced++`，**不移表**） | [2] 读到 ⇒ 立即消费、不阻塞；事件补偿扫描时任务不在表里 ⇒ 无副作用 | ✅ 安全                                                                         |
| [2]~[3b] 之间                | `WAIT` + `Lock==1` | 异步（只记录）                                       | 消费者随后入表；本轮 `EventSched` 已在表中找到它并唤醒               | ✅ 安全（**这正是 `XC_Task.c:252-257` 注释所描述的"先置 BLOCKED 再入表"设计**） |
| [3b] 内（锁内插入期间）      | `WAIT` + `Lock==1` | 异步                                                 | 同上                                                                 | ✅ 安全                                                                         |
| [U] 之后（已入表、锁已释放） | `WAIT` + `Lock==0` | **直接搬表**（目标任务已在表中 ⇒ 搬表合法）         | 立即移入就绪表 + `WAKEUP`/`READY`                                    | ✅ 安全（锁的"角色"正是把中断的移表推迟到插入完成之后）                         |
| [3a] 消费过程中              | `WAIT`/`WAKEUP`    | 非 `WAIT` ⇒ 只记录                                  | 任务不阻塞、继续运行；记录留给下次等待消费                           | ✅ 安全                                                                         |

**结论**：在**计数未接近回绕**的正常状态下，该窗口是安全的——靠"**锁 + 先置 WAIT 再查** + 异步事件补偿"三道机制。这也解释了为什么这个锁必须覆盖到入表完成（`XC_Task.c:236~216`）。

#### A.8.2 现状实现在该窗口**真实会出问题**的唯一情形：A1 的回绕状态

当 `NotifyProduced == 255 && NotifyConsumed == 0`（累积约 255 次未消费，见 A1 的可达场景）时，落在 **[1]~[3b] 锁窗口**内的中断发送会走异步分支：

```c
if(Lock) {
    /* Produced=255, Consumed=0 时: (255+1U)=256 != 0 => 条件成立 => 自增 => 回绕成 0 == Consumed
     * => "有通知"信息被抹掉 */
    if((phTCB->NotifyProduced + 1U) != phTCB->NotifyConsumed) { phTCB->NotifyProduced++; }
    if((phXCOS->EventProduced + 1U) != phXCOS->EventConsumed) { phXCOS->EventProduced++; }
    return (XC_CONTINUE);
}
```
回绕使 `Produced` 变成 `0 == Consumed` ⇒ **"有通知"信息消失**。此处两点更正（本轮复核）：

1. **丢唤醒与 `EventProduced` 是否回绕无关**：即使事件补偿正常（`EventProduced++` 成功、`XC_Sch_EventSched` 被调用），`WAKEUP_NOTIFY` 的判据（`XC_Sch.c:187`）读的同样是 `Produced != Consumed`，回绕后为假 ⇒ **扫描跑到了也扫不醒该任务**；
2. `EventProduced` 本身**几乎不可能**回到"满"状态（主循环每轮 drain，见 §A1 逐站点表）⇒ 它**不是**丢唤醒的必要条件。

⇒ 因此本窗口丢唤醒的**充分条件只有一条**：`NotifyProduced/Consumed` 的未消费量到达 255。此后消费者 [2] 读不到通知 ⇒ 入表阻塞，且**没有任何机制会再唤醒它**（直到下一条通知到达）——**永久性丢唤醒**。

> 这是"等待通知处理中出现发送通知"在**现状实现**下唯一的真实缺陷，也是 A1 必须修的根本原因。

#### A.8.3 单标志方案（附录 A）在同一窗口的表现

生产者只是 `NotifyPending = 1U`（**无条件常量写**，没有判满、没有回绕）：

| 窗口                | 结果                                                                                                              |
| ------------------- | ----------------------------------------------------------------------------------------------------------------- |
| 任一窗口内的置 1    | 要么被 [2] 读到（不阻塞），要么被唤醒路径（异步/直接）捕获；两者都不是"丢弃"                                      |
| 与消费侧的置 0 同时 | 结果非 0 即 1；`1` 保留 ⇒ 下次等待立即返回（良性）；`0` 生效 ⇒ 消费方正在唤醒该任务（任务会运行并读到最新数据） |
| **该窗口的丢唤醒**  | **结构上不可能**（置位永不丢弃）                                                                                  |

#### A.8.4 任务上下文发送（补充）

不能与等待处理并发，只可能发生在整段**之前**或**之后**：
* **之前** ⇒ 命中"提前通知"（等待不阻塞）✅；
* **之后**（目标任务已在表里）⇒ `Lock==0` ⇒ **直接搬表**，立即进就绪表 ✅；
* 发送给"正在运行/在就绪表"的任务 ⇒ 只记录，等它下次 `WaitNotify` 立即返回 ✅。

#### A.8.5 该窗口的验证方法（建议列入回归）

在 `XC_Task_HandleWaitNotify` 的 **[1]/[2]/[3b] 三个点**插桩调用 `XC_Task_SendNotify`（或用一个 hook 在锁窗口内触发），断言：
1. 任务**不得**以"未消费通知"的状态阻塞（`WaitNotify` 返回后 `IsNotifyTimeout()==0`）；
2. `TaskState` 与所在表一致；
3. 若发生"先通知后被挂起"（A2 场景），任务必须保持 `SUSPEND`。

```
1. 任务 A: XC_Cor_WaitNotify(1000) 无通知

2. 中断在锁窗口(主循环 TimeSched/EventSched 期间): XC_Task_SendNotify(A)
   → Lock==1 → 走异步分支: 置 NotifyPending=1 + EventPending=1, 不移表

3. 另一任务(任务上下文, 合法): XC_Task_Suspend(A)
   → TaskState=SUSPEND + 移入阻塞表; 挂起不清通知: NotifyState 仍 WAIT, NotifyPending 仍 1

4. 主循环 EventSched (EventPending 门控触发)
   → WAKEUP_NOTIFY(阻塞表) → A: WAIT && NotifyPending!=0 → 误唤醒!
   → 移就绪表 + NotifyState=WAKEUP + TaskState=READY (覆盖 SUSPEND)
```
**关键点**：`XC_Task_SendNotify` 对"**发送时已挂起**"的任务返回 `XC_FAIL`（先挂起、再通知，确实唤不醒）；本缺陷绕过它是因为**通知先于挂起**发生——挂起动作本身**不清除通知**，于是阻塞表里出现"`SUSPEND` + `WAIT` + 未消费通知"的任务，被事件补偿误唤醒。**全程不需要中断 `Suspend`**（中断只做 `SendNotify`，`Suspend` 由任务上下文调用）。
> 注：本缺陷在原独立文档中按当时字段名（`NotifyProduced/Consumed`、`EventProduced`）记录；2026-09-14 通知改造后字段为 `NotifyPending` / `EventPending`，机理完全相同。

**影响与严重程度**：**中**（触发需"异步 `SendNotify` + 随后 `Suspend` + `EventSched`"外部时序，多出现在中断场景）。
① 破坏"挂起只能被 `Resume` 恢复"的语义，任务可能执行到 `WaitNotify` 之后的关键代码；
② 若任务在误唤醒后再次让出并调用 `XC_Cor_Reset`，还会清栈，挂起彻底失效。

**实测复现（未修复内核）**
```
[Bug#2] A woke-up count = 1 (expect 0); A state = 2 (expect SUSPEND=4)

# 临时副本套用下方方案后:
[Bug#2] A woke-up count = 0 (expect 0); A state = 4 (expect SUSPEND=4)
```

**方案（两处配套，最小；当时已实测有效 —— 后于 2026-09-14 正式实施，见本节末）**
```c
/* 1) XC_Sch.c WAKEUP_NOTIFY 条件追加: 挂起任务不唤醒 */
&& (XC_LIST_TO_TCB(pIterator)->TaskState != (uint8_t)XC_TASK_SUSPEND))

/* 2) XC_Task_Resume 内(锁内)补齐通知状态, 否则恢复后会误报超时 */
if(phTCB->NotifyState == (uint8_t)XC_NOTIFY_WAIT) {
    if(phTCB->NotifyPending != 0U) {
        phTCB->NotifyPending = 0U;
        phTCB->NotifyState    = XC_NOTIFY_WAKEUP;
    }
}
```
> **为何需要改动 2**：仅加改动 1 后，挂起任务能保持挂起，但 `Resume` 恢复时若挂起前留有未消费通知，`NotifyState` 仍为 `WAIT` ⇒ 恢复后 `XC_Cor_IsNotifyTimeout()` 会**误报超时**（明明有通知却报超时）；改动 2 在恢复时补消费，保证通知语义一致。

**决策与用户使用保证（2026-08-24 历史记录；已被 2026-09-14 修复取代）**
* **框架层暂不修复**：完整修复需一并改变 `XC_Task_Resume` 的挂起恢复通知语义，权衡后暂缓；
* **已落地动作**：在 `XC_Sch.c` 的 `WAKEUP_NOTIFY` 宏注释中记录为**已知缺陷（使用注意）**；
* **用户约定**：不要对"处于等待通知（`XC_Cor_WaitNotify`）中、且可能收到异步通知（中断 `SendNotify`）"的任务执行挂起；若必须挂起，先 `XC_Cor_ClrNotify()` 清除通知，或确认无未消费通知。

**注（已在 2026-09-14 修复中同步处理）**：`XC_Sch.c:173-178` 已把本缺陷写成"**已知缺陷（使用注意）**……此路径需用户使用层面保证……**框架暂不处理**"。若采纳上面方案，该注释须同步改写为"已在 `WAKEUP_NOTIFY` 条件中排除 `SUSPEND`"，否则后续读者会以为该行为仍被接受。另：`XC_Task_HandleSuspend`（`XC_Task.c:164-170`）挂起时**不清通知**（`NotifyState` 与待处理标志保持原值），这是本缺陷的另一半根因；修复时需一并决定"挂起期间登记的通知"的归属（丢弃，或留待 `Resume` 后由目标任务消费，即上面方案 2）。

```c
 * @file  20260824_事件调度误唤醒挂起任务_复现测试.c   (源码内联; 存为 repro.c 编译)
 * @brief 复现缺陷 DEF-20260824-02: 挂起任务被 EventSched 误唤醒(应保持 SUSPEND)
 *  触发链: 任务A WaitNotify(WAIT) → 锁窗口异步 SendNotify(仅置待处理标志, 未移表)
 *          → 任务B 挂起 A(阻塞表+SUSPEND, 挂起不清除通知)
 *          → 主循环 EventSched 的 WAKEUP_NOTIFY 误唤醒 A
 * 当前内核: 不修复(已知缺陷), 预期复现 woke-up=1 / state=READY
 * 备选修复后: 预期 woke-up=0 / state=SUSPEND

 */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <time.h>
#include "XCOS.h"
#include "XC_Cor.h"
#include "Internal/XC_Core.h"

/* ===== 自我超时看门狗(防止程序卡死; C标准 clock(), 全平台可编译) ===== */
static clock_t s_WD_Start = 0;
static clock_t s_WD_TimeoutMs = 30000;
static const char* s_WD_Tag = "test";
static void WD_Init(clock_t timeoutMs, const char* tag)
{
    s_WD_Start     = clock();
    s_WD_TimeoutMs = timeoutMs;
    s_WD_Tag       = tag;
}
static void WD_Check(void)
{
    if((clock() - s_WD_Start) >= (clock_t)(s_WD_TimeoutMs * (clock_t)CLOCKS_PER_SEC / 1000)) {
        printf("[WATCHDOG] %s: timeout (>%u ms), kill!\n", s_WD_Tag, (unsigned)s_WD_TimeoutMs);
        fflush(stdout);
        exit(2);
    }
}

XCOS_t g_xc;

static XC_TaskCB_t s_TCB_A;
static XC_TaskCB_t s_TCB_B;
static int s_Bug2_AWokeUp = 0; /* A 被非 Resume 方式唤醒次数(期望 0) */

void Task_A(XC_TaskHandle_t t)
{
    XC_Cor_Enter(t);
    XC_Cor_WaitNotify(0U); /* 死等通知 -> 阻塞表, NotifyState=WAIT */
    s_Bug2_AWokeUp++;      /* 若执行到此处 = 被误唤醒(挂起被破坏) */
    while(1) {
        WD_Check();
        XC_Cor_Yield();
    }
    XC_Cor_Leave();
}

void Task_B(XC_TaskHandle_t t)
{
    XC_Cor_Enter(t);
    /* 模拟: 中断在"调度器锁窗口"SendNotify(A)(异步登记), 随后任务上下文 Suspend(A) */
    XC_Core_Lock(&g_xc);                /* 锁=1: 模拟主循环锁区(中断) */
    XC_Task_SendNotify(&s_TCB_A, NULL); /* A WAIT -> 异步登记(置待处理标志, 不移表) */
    XC_Core_Unlock(&g_xc);
    XC_Task_Suspend(&s_TCB_A);          /* A -> 阻塞表 + SUSPEND(仍 WAIT, 标志仍为 1) */
    XC_Cor_Yield();                     /* 让出 -> 主循环 EventSched 触发 */
    /* 再次调度: 检查 A 是否被 EventSched 误唤醒 */
    printf("[Bug#2] A woke-up count = %d (expect 0); A state = %d (expect SUSPEND=%d)\n",
           s_Bug2_AWokeUp, (int)XC_Task_GetState(&s_TCB_A), (int)XC_TASK_SUSPEND);
    exit(0);
    XC_Cor_Leave();
}

int main(void)
{
    WD_Init(10000, "DEF-20260824-02 repro");
    printf("===== XCOS DEF-20260824-02 Repro =====\n");
    memset(&g_xc, 0, sizeof(g_xc));
    XC_Sch_Init(&g_xc);
    XC_Task_Reg(&g_xc, &s_TCB_B, Task_B, NULL); /* 就绪表 [B] */
    XC_Task_Reg(&g_xc, &s_TCB_A, Task_A, NULL); /* 就绪表 [A, B] */
    /* 轮1: A 运行 WaitNotify 死等 -> 阻塞表
     * 轮2: B 运行(锁窗口 SendNotify + Suspend) -> 让出
     *      主循环 EventSched -> 若误唤醒 A 则下一轮 A 运行(记录)
     * 轮3: A(若被唤醒) / 轮4: B 检查 */
    XC_Sch_Start(&g_xc);
    return 0;
}
```

### A9 "提前通知"与"等待中通知"的唤醒优先级不一致

**状态**：✅ **已解决（已修复，2026-09-14）** —— 用户决策：**照 V2.0 全统一表尾**（协作式应以公平轮转为主，含 idle）。实现为"**任何任务进入就绪表一律排队尾**"，消除了"唤醒/定时/复位/恢复插队"这一**语义漂移**（V2.1.0 重构引入），同时消除了过载下"通知任务独占调度器、其它任务与 idle 被饿死"的风险。

**证据**：
* 等待中被唤醒 ⇒ `XC_Task_MoveToReadyList`（`XC_TaskInternal.h:97`，**插就绪表首**）⇒ 下一轮**优先**运行；
* 提前通知命中 ⇒ 任务**不阻塞**、自身 `COR_SetBPBreak` 让出 ⇒ 走"归位"`XC_SCH_PUT_TAIL`（`XC_Sch.c:282`，**插表尾**）⇒ 需等本轮其它就绪任务跑完。

**影响**：同为"通知"，两种到达时序的调度优先级不同，**时序不可预期**且难测试。
**方案（二选一）**
1. **统一为"唤醒优先"**：归位逻辑识别"本轮是通知命中"（TCB 加一标志位）⇒ 同样插表首；
2. **明确文档**：在 API 文档与 `Docs/Skill/XCOS_Agent_Skill.md` 写明"提前通知=普通让出（表尾）；等待中通知=唤醒优先（表首）"。

**实施记录（2026-09-14；决策：统一表尾，回归 V2.0 语义）**

*1) 版本溯源（关键）*：**V2.0 就是"入表即排队尾"，且只有一条规则** ——

| 版本                 | 就绪表机制                                                                                                                                 | 入表规则                                                                                                                |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| V2.0                 | 跨轮游标 `pPrevReadyNode`（`XC_TaskInternal.h` 单一宏 `XCTask_MoveTaskToReadyList` = `XCList_MoveNodeAfter(phXCOS->pPrevReadyNode, ...)`） | **统一：排在"本轮已排队者之后" = 队尾**；`PUT_TAIL` 之类宏在 V2.0 **不存在**                                            |
| V2.1.0（本项修改前） | 去掉游标（取表首 + 摘除游离化 + 自环判定归位，修 DEF-20260821）                                                                            | **分裂**：归位/提前通知 = 表尾；**唤醒/定时/复位/恢复/注册 = 表首**（宏名沿用，目标由"游标"改成"表根" ⇒ **语义漂移**） |

⇒ 本项不是"新增设计"，而是**把 V2.1.0 重构时丢掉的语义找回来**；游标机制本身有缺陷（DEF-20260821），**不恢复游标**。

*2) 改动点（全部改为排队尾）*

| --------------------------------------------- | ---------------------- | ---------- | ------------------------------- |
| `XC_Task.c` `XC_Task_AddInternal`             | 注册                   | 插表首     | `XC_Task_InsertToReadyListTail` |

| `XC_Task.c` `XC_Task_Resume`                  | 恢复挂起               | 插表首     | 同上                            |
| `XC_Task.c` `XC_Task_SendNotify`              | 等待中通知（直接路径） | 插表首     | 同上                            |
| `XC_Sch.c` `WAKEUP_NOTIFY`（EventSched）      | 锁窗口内到达的通知     | 插表首     | 同上                            |
| `XC_Sch.c` `XC_Sch_TimeSched`                 | 延时/超时到点唤醒      | 插表首     | 同上                            |
| `XC_Sch.c` `XC_Sch_TimeSched`（溢出回绕整表） | Tick 溢出批量搬表      | 整表到表首 | 整表**追加到表尾**              |
