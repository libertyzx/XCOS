## 二、内核缺陷

### A19 跨回绕延时的溢出表可能永不排空（任务永不唤醒）

**状态**：✅ **已修复（2026-09-17）** —— `Code/Src/XC_Sch.c`：`XC_Sch_TimeSched` 末尾**每轮**更新 `PrevTick`（删除"仅在回绕分支/到点分支更新"的两处）。

**证据**：`XC_Sch.c:103`（`PrevTick > Tick` 是**唯一**的回绕判定）/`:117`（溢出表整表搬入时间表，**唯一**的排空点）/`:119`、`:145`（原先仅此两处更新 `PrevTick`）。
**触发链**：
1. 应用**启动后从未有定时到点**（例如纯事件驱动：只用 `WaitNotify(0)` 死等）⇒ `:145` 分支从未执行；
2. 期间有一笔**跨回绕**的延时（`Tick + 延时 > 2³²`）⇒ `XC_Task.c:246` 判定"溢出" ⇒ 节点进**溢出表**；
3. Tick 真正回绕时 `PrevTick` 仍是初值 `0`（`XC_Sch.c:233` 由 `XC_Sch_Init` 置）⇒ `PrevTick > Tick` 不成立 ⇒ **整表搬移被跳过**；
4. ⇒ 该任务在溢出表里**永不排空**（最长再等一个完整回绕周期，若期间仍无到点则**永久**挂死）；同时空闲提示值按"模块差"算出巨值（实测 `0xFFFFFF00`）。

**后果**：单任务永久挂死（比"延时变短"更难定位：任务不报错、只是不再运行）；回绕周期随 `XC_CFG_TICKS_PER_SEC` 缩短（10 kHz ≈4.97 天、100 kHz ≈11.9 小时）⇒ 触发窗口比"49.7 天"近得多。

**复现与验证**：用例 `Docs/问题跟踪/修正方案/20260917_复核十项修正/测试/20260917_跨回绕溢出表_复现测试.c`（已入 `Tests/manifest.txt`：`A19-跨回绕溢出表`）。
- **修复前（prefix 内核实测）**：`PrevTick=0x00000000`（期望 `0xFFFFFF00`）、回绕后提示值 `0xFFFFFF00`、任务入口只执行 1 次 ⇒ **failures 4**（FAIL）；
- **修复后**：`PrevTick` 每轮更新、回绕后提示值 512、任务被唤醒 ⇒ **failures 0**（PASS）。

### A20 空闲提示值的"当前 Tick"仍在锁外取（A17 残留）

**状态**：✅ **已修复（2026-09-17）** —— `Code/Src/XC_Sch.c`：空闲分支改为"**先加锁，再取 Tick 快照**"（与"就绪表是否空 / 下个唤醒时刻"读成一次原子观察），并把 `else` 嵌套压平。

**证据**：修复前 `XC_Sch.c:326` 取 Tick 在 `:331` 加锁**之前**；若这期间中断推进了 Tick，`Next - Tick` 被**高估** ⇒ 交给 `fIdle` 的"建议休眠上限"偏大 ⇒ 应用可能睡过头（A17 只把**表内取值**并入锁域，Tick 快照是残留项）。
**影响**：偏差有界（≤ 一次空闲回调到实际休眠之间的耗时，通常 µs~ms 级），且契约本就声明"提示值是快照/上限" ⇒ 定级 **低**；但既已在锁内取表，顺手把 Tick 也并进去的成本仅一次 `volatile` 读 ⇒ 采纳。
**验证**：`A17-空闲Tick` 与 `A19-跨回绕溢出表` 覆盖空闲分支的全部取值路径（跨 tick 钳位、回绕钳位、溢出表提示、就绪表判空）⇒ 全 PASS。

### A21 通知的"先写数据 → 再置标志"缺编译器可见性保证

**状态**：✅ **已修复（2026-09-17）** —— `Code/Inc/Internal/XC_TypeInternal.h`：`pNotifyData` 加 `volatile`（字段注释给出理由与"硬件层重排仍需用户屏障"的边界）。

**证据**：`XC_Task.c:702-703` 先写 `pNotifyData`、再写 volatile 的 `NotifyPending`；消费侧 `XC_Cor.h:280`（读数据）与 `:271`（读状态）。C 标准只保证 **volatile 访问之间**的相对顺序 —— 非 volatile 的"数据写"允许被编译器**重排到标志写之后** ⇒ 消费侧见到标志后可能读到旧数据（原文档把这一点写成"纯契约、靠调用者假设"）。
**影响**：Cortex-M3（单核、强序、无 D-Cache）下**硬件**重排不是问题 ⇒ 只有**编译器**重排风险，概率低但非零；`volatile` 代价为 0 字节、每次访问仍是单条访存 ⇒ 采纳。
**验证**：`A1-通知回归` / `A2-挂起优先级` / `B1` 通知相关用例全 PASS；对象级 `XC_Task.o` 体积未因该项变化（`volatile` 不生成额外代码）。

### A22 未初始化 TCB 的野指针写风险

**状态**：✅ **已修复（2026-09-17）** —— 嵌套配置的**落点**在四条入口上对齐（并新增用例 `A22-嵌套注册` 锁定）：
- `XC_Task_Reg`（无嵌套入口）：清空 `pCorStack`/`CorDepthMax` ⇒ 未清零 TCB 上的垃圾配置不会存活；
- `XC_Task_RegExt`：改为**先 `Reg` 成功、再写帧栈**（原实现先写配置再 `Reg`，会被 `Reg` 的清空逻辑抹掉 ⇒ **嵌套能力静默失效**，是本批自查发现并修掉的回归）；
- `XC_Task_SetEntry`（分步注册第一步）：在**未注册**的 TCB 上清空 `pCorStack`/`CorDepthMax`（已注册任务"换入口"不动帧栈，嵌套能力保留）；
- `XC_Task_SetCorStack`：写配置并复位 `CorDepth`/`CorState`；
- `CorDepth`/`CorState` 由 `XC_Task_BasicInit` 统一复位（Add/Remove/Reset 都经它）；
- 顺序规则写进头文件与手册：**`XC_Task_SetEntry` →(需要嵌套再)`XC_Task_SetCorStack` → `XC_Task_Add`**；`XC_Task.h` / `XCOS.md` 写明"**TCB 必须静态分配（BSS 零初始化）或先清零**"。

**证据**：`XC_Task_Reg` 的判重（`XC_Task.c:369`，读 `phXCOS`）⇒ 未清零内存可能被当成"已注册"而莫名 `XC_FAIL`；`XC_Task_BasicInit` **不**清 `pCorStack`/`CorDepthMax`（`:54` 注释明确"保留"—— 这是刻意的：`Reset`/分步注册要保住用户的帧栈配置），于是未清零 TCB + 垃圾 `CorDepthMax>0` + 垃圾 `pCorStack` ⇒ `PushFrame`（原判据只比容量）按脏容量写到**野指针**。
**修复取舍**：`Add`（分步注册）**不能**清帧栈（否则会抹掉"先 `SetCorStack` 再 `Add`"的配置）⇒ 该路径以**文档契约**收口；`XC_Task_Reg`（无嵌套入口）可以清 ⇒ 注册即把"帧栈/容量"落成确定值。**不在 `PushFrame` 里加"脏配置"分支**：那属于"前提是契约被破坏"的防御代码（违背本项目既定纪律：契约被破坏应修契约/文档，而不是在热路径兜底），也与 `pCorStack`/`CorDepthMax`"同为有/同为无"的契约重复。
**未闭环（明确记录）**：判重那半仍是"垃圾 `phXCOS` 非空 ⇒ 误判已注册"，框架**无法**区分"垃圾"与"已注册"（除非新增魔数字段 ⇒ 动布局，不做）⇒ 以**文档契约**收口。
**验证**：`B1-开启`（帧栈越界上报）、`B3-开启`（嵌套自洽检查项）、`B4-全开`、`A1-嵌套关闭` 全 PASS。

## 三、健壮性 / 诊断

### B5 自检在任务上下文必然误报 `XC_CHK_TASKNUM`

**状态**：✅ **已修复（2026-09-17）** —— `Code/Src/XC_Diag.c`：节点总数允许"恰好比 `TaskNum` 少 1"；其余差值/超上限照报。

**证据**：`XC_Diag.c:194`（原判据 `NodeCnt != TaskNum` ⇒ 报 `XC_CHK_TASKNUM`）；`XC_Sch.c:265` `XC_SCH_TAKE_FIRST` 把运行中的任务**自环游离**（不在任何表内）而 `TaskNum` 仍含它 ⇒ **任务内调用必然差 1**；而 `XC_Config.h` 的推荐用法①恰是"**每个 API 调用之后**调一次"（任务里正是 API 调用最密集的地方）⇒ **推荐用法与实现互相矛盾**，排障时会被引到错误方向。
**修复取舍**：容忍值**恰为 1** ⇒ 任务上下文下"`TaskNum` 虚高 1"这类真实漂移**仍会**被抓到（差值会变成 2）；盲区只剩"非任务上下文 + 恰好差 1"，其代价小于"推荐用法在任务里不可用"。
**复现与验证**：用例 `Docs/问题跟踪/修正方案/20260917_复核十项修正/测试/20260917_任务内自检_回归测试.c`（已入 `Tests/manifest.txt`：`B5-任务内自检`）。
- **修复前（prefix 内核实测）**：任务内自检返回 `4`（= `XC_CHK_TASKNUM`）⇒ **failures 1**（FAIL）；
- **修复后**：任务内自检 `XC_CHK_OK`；并**注入** `TaskNum++` 后仍报 `XC_CHK_TASKNUM`（证明容忍值恰为 1）⇒ PASS。

## 四、配置

### C5 Tick 类型"可配"是假配置（64 位可编过，但坏）

**状态**：✅ **已修复（2026-09-17）** —— `Code/Inc/XC_Config.h`：**删除**配置宏 `XC_CFG_TICK_TYPE` 与配套编译期断言；`XC_Tick_t` 改为**硬编码** `uint32_t` 并**移到类型层** `Code/Inc/Internal/XC_TypeInternal.h`（与其它框架类型同层；用户经 `XC_Type.h` / `XCOS.h` 一样可见）。

**背景**：C4（2026-09-14）用 `sizeof(XC_Tick_t) >= 4U` 拦住了 16 位，但**放过了 64 位**；复核确认 64 位在该实现下不是"功能受限"而是**功能损坏**：

| 机制                 | 代码位置                           | 64 位下的后果                                                                                      |
| -------------------- | ---------------------------------- | -------------------------------------------------------------------------------------------------- |
| 入口判定用截断值     | `XC_Task.c:232`、`:246`            | `TickCount` 形参是 `uint32_t` ⇒ 大延时**静默变短**；运行超过 2³² 个 Tick 后判定恒为"溢出"       |
| 排空只靠 Tick 回绕   | `XC_Sch.c:103`、`:117`             | 64 位实际上永不回绕 ⇒ 溢出表**永不排空** ⇒ 约 49.7 天（1 kHz）后**所有带超时的阻塞全部挂死**     |
| 读的原子性           | `XC_Time.h:42`（直接读全局计数）   | 64 位读会被中断在两半之间改写 ⇒ **撕裂值**（32 位对齐读在 Cortex-M 上单次原子）                   |
| 哨兵常量             | `XC_Task.c:48`、`XC_Sch.c:343`     | `~0U`（`0xFFFFFFFF`）不是 64 位最大值 ⇒"按最大时间休眠 / 一直阻塞"语义失真                        |
| RAM                  | `XC_Tick_t` 字段                   | `XCOS_t.PrevTick` +4 B、**每任务** `TaskWakeupTick` +4 B ⇒ 与"最省"基线相悖，换来的是坏行为       |

**决策（方案 B）**：不再保留"可配"这一宣传面 —— 宏删除 + 固定类型 + `== 4U` 断言。
- **兼容性**：宏名删除只影响"在 `XCOS_Cfg.h` 里定义过它"的工程（**仓内无任何工程这么做**，全仓仅 `XC_Config.h` 一处定义点）⇒ 这类工程删掉那一行即可；`XC_Tick_t` 的用法与所有 API 完全不变；
- **为什么"要跑很多年"不需要 64 位**：比较类 API 全是**无符号减法**语义（回绕安全），跨回绕延时由溢出表支持 ⇒ 只要**单次**超时 < 回绕周期即可**无限期**运行；32 位也正是硬件计数器（SysTick 24 位 / TIM 16·32 位）的原生宽度；
- **若将来真要做 64 位**：那是**特性**（需统一全部计数形参、删除/重写溢出表、Tick 读改"高低半重试"、哨兵改 `XC_TICK_MAX`、全套基线重测）⇒ 走 `Docs/ROADMAP.md`，不要再放回配置开关。

**验证**：`Docs/XC_Config.md`「XC_Tick_t」、`Docs/XCOS.md` 类型表（来源列改为 `XC_Type.h`）、`Docs/架构概览` 的类型片段、`Tests/baseline.md` 已同步；默认配置下 **0 告警**；类型移层 + 删断言均 **0 代码 / 0 RAM**（断言本就不产码）。
