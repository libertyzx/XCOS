### A7 `XC_Task_Reg` / `XC_Task_Add` 不检测重复注册

**状态**：✅ **已修复（2026-09-14）** —— `XC_Task_Reg` / `XC_Task_Add` 均加"重复注册检测"（判据 `phTCB->phXCOS != NULL`），重复时返回 `XC_FAIL`；**无新增字段/API/配置开关**。

**本次落地（2026-09-14）**
* **代码**：`Code/Src/XC_Task.c`
  - `XC_Task_Reg` 开头（任务数上限判断**之前**）：`if(phTCB->phXCOS != NULL) { return (XC_FAIL); }`
  - `XC_Task_Add` 开头：同一判据；
  - **为何用 `phXCOS` 而非 `TaskState`**：`Reg` 会先把 `TaskState` 写成 `VOID`（原逻辑），状态判据无效；而 `phXCOS` 注册后非空、`XC_Task_HandleRemove` 会清 `NULL` ⇒ 同时覆盖"已注册"与"移除后可重注册"两种语义；
* **验证（宿主 gcc，before/after 对照）**：

  | 版                 | checks / failures | 二次 `Reg`   | `TaskNum` | 就绪表节点数          | `Reg→Remove→Reg` | 重复 `Add`   |
  | ------------------ | ----------------- | ------------ | --------- | --------------------- | ------------------ | ------------ |
  | before（去掉判据） | 9 / **6**         | `0`(OK) ✗   | **2** ✗  | **32（遍历成环）** ✗ | OK                 | `0`(OK) ✗   |
  | after（含判据）    | 9 / **0** ✅      | `1`(FAIL) ✅ | **1** ✅  | **1** ✅              | OK ✅              | `1`(FAIL) ✅ |

  > before 版"就绪表节点数 = 32"是因为**同一节点被重复插入导致链表成环**，遍历不收敛（测试里以 32 次上限截断）——这正是本条"后果"的实证；
* **回归**：通知回归（18 项 ALL PASS）、状态一致性回归（输出不变）、A2 语义测点（20 项）全部通过；MDK 全量重建 0 错误（体积增量见文末）。

**证据**：`XC_Task.c:300-313`（`Reg`）、`XC_Task.c:414-423`（`Add`）都只判任务数上限；头文件明确警告"**不可多次注册同个任务(没有做重复判断,会发生未知情况)**"。
**后果**：同一 TCB 二次入表 ⇒ 同一 `ListNode` 被挂进同一张表两次（或两张表）⇒ 自环/节点重复 ⇒ 同一任务被调度两遍、`MoveNodeAfter` 破坏链。
**方案**（利用既有字段，注册前 `phXCOS==NULL` 且状态 `VOID`；移除后会复位，故可重新注册）：
```c
if((phTCB->phXCOS != NULL) || (phTCB->TaskState != (uint8_t)XC_TASK_VOID)) { return (XC_FAIL); }
```
**验证**：连续两次 `XC_Task_Reg` 同一 TCB ⇒ 第二次返回 `XC_FAIL`、`XC_Sch_GetTaskNum` 不变。

**体积/仿真实测（MDK AC5 -O1，STM32F103ZE / SARMCM3）**

| 项                                | 基线（A7 前）    | A7 后            | 差                |
| --------------------------------- | ---------------- | ---------------- | ----------------- |
| `Code`                            | 3148 B           | **3156 B**       | **+8 B**          |
| `RO-data` / `RW-data` / `ZI-data` | 336 / 112 / 1608 | 336 / 112 / 1608 | **0**             |
| 仿真（A2 语义测点 14 项）         | failures = 0     | failures = 0     | 0（语义无副作用） |
| 构建告警                          | 0 内核告警       | 0 内核告警       | —                |

> 即：**两个判据共 8 字节 Flash，0 RAM**；重复注册从"静默破坏链表"变为"返回 `XC_FAIL`"。

### A8 `XC_Task_SetEntry` 可在"嵌套中"破坏"栈底帧 = 顶层入口"不变量

**状态**：✅ **已修复（2026-09-14，方案 A）** —— `XC_Task_SetEntry` 内**先清栈 + 重置断点**再写新入口；语义显式化为"**嵌套中换入口 = 丢弃当前嵌套层，按新入口从头运行**"；**无 API 变更**。

**证据**：`XC_Task.c:395-400`（只改 `fTask/pParam`，不动 `CorDepth/pCorStack`）；`XC_Task.c:63-81`（`PushFrame` 依赖 `pf->pfn = phTCB->fTask` 记录"父层入口"，且注释声明"栈底帧恒为顶层任务"）。
**后果**：嵌套中改入口后，`HandleReset/HandleRemove`（`XC_Task.c:130-133`、`:151-154`）用 `pCorStack[0].pfn`（**旧入口**）恢复 ⇒ 任务跳回旧函数或语义错乱。
**方案**：`SetEntry` 中若 `CorDepth > 0` 则**先清栈**（`fTask = pCorStack[0].pfn; CorDepth = 0U;`）或直接返回失败。

## 详细分析（2026-09-14 复核）

### 1. 不变量，以及它是怎么被破坏的

* **不变量**："**栈底帧 = 顶层入口**" —— `pCorStack[0].pfn` 是**顶层入口的缓存副本**：只在**第一次** `XC_Cor_Call` 时写入
  （`PushFrame`：`pf->pfn = phTCB->fTask`，`XC_Task.c:75`；`CorDepth==0` ⇒ 写 `frame[0]`），此后
  `PopFrame`(`:92`)、`HandleReset`(`:152`)、`HandleRemove`(`:130`) 都以 `pCorStack[0].pfn` 作为"回到最外层"的凭据。
* **破坏者**：`XC_Task_SetEntry`(`:399-404`) 只写 `TaskState = VOID; fTask = fTask; pParam`，
  **既不清 `CorDepth`、也不更新 `pCorStack[0].pfn`** ⇒ 当任务处于"**嵌套中**"（`CorDepth > 0`）时，`frame[0].pfn` 仍是**旧入口**。

### 2. 触发链（逐函数）

| #   | 动作                                                                                               | 状态                                                                                                                                                                |
| --- | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `XC_Task_RegExt(&A, TaskTop, …, s_Stack, 2U)`                                                     | 帧栈就绪                                                                                                                                                            |
| 2   | A 顶层 `XC_Cor_Call(Sub)` ⇒ `PushFrame`                                                           | `frame[0].pfn = TaskTop`（缓存）、`fTask = Sub`、`CorDepth = 1`                                                                                                     |
| 3   | A 在子层 `DelayMs`/`WaitNotify` 让出                                                               | `CorDepth` 仍为 1（**嵌套中**）                                                                                                                                     |
| 4   | **另一任务** `XC_Task_SetEntry(&A, TaskTopNew, NULL)`                                              | `fTask = TaskTopNew`、`TaskState = VOID`；**`CorDepth` 与 `frame[0].pfn` 未动** ⇒ 不变量已坏                                                                       |
| 5a  | 外部 `XC_Task_Reset(&A)`                                                                           | **空操作**（`:457` 有 `TaskState != VOID` 守卫，而 `SetEntry` 已把状态置 `VOID`）⇒ 深度(仍 1)/断点(脏)残留 ⇒ **新入口不生效、任务僵死**（实测 `newEntryRan = 0`） |
| 5b  | `XC_Task_Remove(&A)` ⇒ `HandleRemove`（**无 VOID 守卫**，`:377` 只判 `phXCOS`）                   | 执行 ⇒ `fTask` 被 `pCorStack[0].pfn` 写回**旧入口**；随后 `phXCOS=NULL`，下次 `Reg` 沿用旧入口 ⇒ 新入口丢失（实测 `fTask==New? = 0`）                             |
| 5c  | 自复位 `XC_Cor_Reset()` / 嵌套越界保护（`PushFrame` 的 `CorDepth >= CorDepthMax`）⇒ `HandleReset` | 同样按 `pCorStack[0].pfn` 恢复 ⇒ 回旧入口（"安全降级"的降级目标错）                                                                                                |

**附带副作用**：`SetEntry` 会把**运行中**任务的 `TaskState` 清成 `VOID`（分步注册的既有契约）⇒ 该任务既不在任何表里、`phXCOS` 又非空
⇒ 形成"**僵尸**"：`Resume` 返回 FAIL、也无法重新注册（A7 起 `Reg`/`Add` 对已注册 TCB 返回 FAIL），只能靠 `Reset`/`Remove` 复位。

### 3. 方案对比

| 方案          | 做法                                                                                                                                                               | 成本 / 风险                                             |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------- |
| **A（推荐）** | `SetEntry` 内**先清栈 + 重置断点**，再写新入口：`CorDepth = 0U; COR_Init(BP); fTask = …; pParam = …;`（语义：**嵌套中换入口 = 丢弃当前嵌套，按新入口从头运行**） | 3~4 行（+2 次写）≈ **+8 B Flash / 0 RAM**；无 API 变更 |
| B             | 仅强化文档（现有注释已提示"换前须先清栈"）                                                                                                                         | 0 代码；隐患仍在（被动）                                |
| C             | 改签名返回 `XC_Return_t`，`CorDepth > 0` 时拒绝                                                                                                                    | **破坏 API 兼容** ⇒ 不建议                             |
| D             | 不动                                                                                                                                                               | 保持现状（隐患 + 僵尸路径）                             |

### 4. 验证设计（可执行，沿用现有双通道）

* **复现用例（宿主 gcc）**：A 用 `RegExt` 配栈 → 顶层 `Call(Sub)` → 子层 `DelayMs` 让出（`CorDepth=1`）→ B 调 `SetEntry(&A, NewTop, NULL)` → B 调 `Reset(&A)`；
  用静态标记观测 A **从哪个函数开始继续运行**：
  - 现状：从 **`CorTop`（旧入口）** 开始 ⇒ 复现本条；
  - 方案 A：从 **`NewTop`** 开始 ⇒ 通过；
  另测 `Remove` 路径：`Remove` 后读 `fTask`——现状为旧入口、方案 A 为新入口。
* **回归**：既有三套用例 + MDK 全量重建（体积 delta）+ MDK 仿真语义测点。

## 本次落地（2026-09-14，方案 A）

**代码**（`Code/Src/XC_Task.c` `XC_Task_SetEntry`，`+4 B` 对象级）

```c
phTCB->TaskState = XC_TASK_VOID; // 任务状态清除
phTCB->CorDepth  = 0U;           // 丢弃当前嵌套帧(栈底帧不变量: [0].pfn == 最外层入口)
COR_Init(phTCB->BP);             // 重置断点(避免脏断点跳入新函数的非法位置)
phTCB->fTask     = fTask;        // 更新任务入口
phTCB->pParam    = pParam;       // 传递给任务的参数
```

### A12 `XC_CFG_TICKS_PER_SEC` 不整除 1000 时，ms 换算系统性失真

**状态**：✅ **已修复（2026-09-14，方案 A+B）** —— 分支 ① 增加**编译期断言** `(1000U % XC_CFG_TICKS_PER_SEC) == 0U`（0 运行时代价）；文档补"支持频率表"并修正 `XC_Config.md` 的范围描述。

**证据**：`XC_TimeInternal.h:37-38`（`XC_TICK_PERIOD_MS = 1000U / XC_CFG_TICKS_PER_SEC`，**整型除法**）。
**例子**：`XC_CFG_TICKS_PER_SEC = 800` ⇒ `TICK_PERIOD_MS = 1`（实际 1.25 ms）⇒ `XC_Time_TicksToMs()`/`XC_Time_GetMs()` 系统性偏小 **20%**（1 秒实测报 800ms）；而 `MsToTicks` 因向上取整仍可用（1ms → 1 tick）。
**方案**：编译期断言"`1000 % XC_CFG_TICKS_PER_SEC == 0`"（或在文档里明确"支持 1/2/4/5/8/10/20/25/40/50/100/125/200/250/500/1000 Hz"），并给 `TicksToMs` 提供用 64 位中间量的精确实现作为可选宏。

**本次落地（2026-09-14，方案 A+B）**：采纳**编译期断言 + 文档频率表**；**未采纳**方案 C（64 位精确换算，见下文权衡）。

### 实测：反向测试（宿主 gcc，逐个频率编译）

| `TICKS_PER_SEC`              | 结果                                             | 说明                           |
| ---------------------------- | ------------------------------------------------ | ------------------------------ |
| 1000 / 500 / 250 / 200 / 125 | ✅ 编译通过                                      | 1000 的因子（分支 ①）         |
| **800 / 600 / 750**          | ⛔ **编译报错**（`XC_TimeInternal.h:51` = 断言） | 非因子 ⇒ 会被"整 ms 截断"失真 |
| 2000 / 3000 / 1000000        | ✅ 编译通过                                      | 走 **us** 时基分支（②）       |
| 2000000                      | ⛔ 编译报错（原有 `#error`）                     | 超出 1e6 上限                  |

| 其他检查                    | 结果                                                                                                          |
| --------------------------- | ------------------------------------------------------------------------------------------------------------- |
| MDK 全量重建（默认 1000Hz） | `Code=3156 RO-data=336 RW-data=112 ZI-data=1608`，与改动前**一致**（断言为 typedef，不产生代码/数据）；0 错误 |
| 宿主回归                    | 通知回归 18 项 ALL PASS、状态一致性回归不变、A2 语义测点 20 项通过                                            |


**破坏性提示**：现有 **800/600/750 Hz** 等配置将**编译报错**；迁移建议改用 **1000 Hz 或 500 Hz**（或 >1000 Hz 的高频档）。

## 后续发现（2026-09-14 探针实测，已另立 A16）

本条收口后的频率探针（`f = 1000/500/2000/4000/10000` 各打印一次换算宏值）发现 **分支 ②（`f > 1000`）本身也有缺陷**：

| `f`   | `MsToTicks(1)` 实测 / 应为 | `SecToTicks(1)` 实测 / 应为 | `TicksToMs(1000)` 实测 / 应为 |
| ----- | -------------------------- | --------------------------- | ----------------------------- |
| 2000  | **2000** / 2               | **2 000 000** / 2000        | **0** / 500                   |
| 4000  | **4000** / 4               | **4 000 000** / 4000        | **0** / 250                   |
| 10000 | **10000** / 10             | **10 000 000** / 10000      | **0** / 100                   |

⇒ 该分支的 `MsToTicks`/`SecToTicks` **1000× 偏大**、`TicksToMs`（及 `TicksToSec`）在 `t < f` 时**恒为 0**；
默认配置为 1000 Hz ⇒ 仓库内长期未暴露。详见**本文件 § A16**（含修法与验证设计）。

**验证**：配置 800Hz 编译 ⇒ 断言报错（或文档说明范围内正确）。

## 详细分析（2026-09-14 复核）

### 1. 真实实现：**两个分支**（原文只覆盖了第一个）

| 分支                            | 条件                           | 时基与换算                                                                                                                                              | 精度                                                                                                                                                                                    |
| ------------------------------- | ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ①（`XC_TimeInternal.h:35-51`） | `XC_CFG_TICKS_PER_SEC <= 1000` | `XC_TICK_PERIOD_MS = 1000U / f`（**整型截断**）；`MsToTicks(ms) = (ms + PERIOD_MS - 1) / PERIOD_MS`（**向上取整**）；`TicksToMs(t) = t * PERIOD_MS`     | **仅当 `1000 % f == 0` 才精确**；否则**双向失真且方向相反**                                                                                                                             |
| ②（`:56-68`）                  | `1000 < f <= 1000000`          | `XC_TICK_PERIOD_US = 1000000U / f`；`MsToTicks(ms) = ms * f`（**精确**）；`TicksToMs(t) = t / f`（向下取整 ≤1ms 误差）；`TicksToUs(t) = t * PERIOD_US` | ⚠️ **原判"基本正确"有误**：2026-09-14 探针实测发现该分支 `MsToTicks`/`SecToTicks` **1000× 偏大**、`TicksToMs` 在 `t < f` 时恒为 **0** ⇒ 已另立条目 **A16** 跟踪（见下文"后续发现"） |
| ③                              | `f > 1000000`                  | `#error "系统每秒滴答数设置错误!"`                                                                                                                      | 已有保护 ✅                                                                                                                                                                             |

⇒ **A12 的真实问题只在分支 ①：`f <= 1000` 且 `1000 % f != 0`**。

### 2. 分支 ① 的失真量化（`MsToTicks` 与 `TicksToMs` 方向相反）

| `f` (Hz) | `PERIOD_MS`（截断） | 实际每 tick | `TicksToMs` 偏差            | `MsToTicks(1)` 实际延时              |
| -------- | ------------------- | ----------- | --------------------------- | ------------------------------------ |
| 1000     | 1                   | 1 ms        | 0 ✅                        | 1.00 ms ✅                           |
| 500      | 2                   | 2 ms        | 0 ✅                        | 2.00 ms ✅                           |
| 800      | 1                   | 1.25 ms     | **偏小 20%**（1s 报 800ms） | 1.25 ms（**偏长 25%**）              |
| 750      | 1                   | 1.333 ms    | 偏小 25%                    | 1.33 ms（偏长 33%）                  |
| 600      | 1                   | 1.667 ms    | 偏小 40%                    | 1.67 ms（**偏长 67%**）              |
| 300      | 3                   | 3.333 ms    | 偏小 10%                    | 3.33 ms（请求 1ms ⇒ **偏长 233%**） |
| 101      | 9                   | 9.901 ms    | 偏小 9%                     | 9.90 ms（请求 1ms ⇒ **偏长 890%**） |

**注意**：`MsToTicks` 的偏长幅度在"**小 ms 请求**"时最大 —— 它向上取整到**整 tick**，而 1 tick 可能是数毫秒（300Hz ⇒ 1 tick = 3.33ms；101Hz ⇒ 9.9ms）；请求值接近 tick 整数倍时误差自然变小（如 300Hz 下 `MsToTicks(3)` = 1 tick ⇒ 偏差 11%）。

**结论**：`TicksToMs`（以及 `XC_Time_GetMs()`）**偏小**，而 `MsToTicks`（延时/超时入参）**偏长** ⇒ 同一次"请求 1ms 延后测已运行 ms"会不自洽。

### 3. 影响面

* **受影响**：`XC_Time_GetMs()`（= `TicksToMs(GetTick())`）、`XC_Time_TicksToMs()`、`XC_Time_TicksToUs()`、`XC_Time_UsToTicks()`，以及所有基于它们的延时/超时**入参换算**（`XC_Cor_DelayMs`/`DelaySec`/`WaitNotifyMs`/`BlockDelayMs`、软件定时器 `TimerSetMs` 等）⇒ 延时比请求偏长；
* **不受影响**：`XC_Time_CheckTimeout()` / `GetRemain()` / `GetElapsed()` 与 `XC_Cor_DelayTick()`——它们是 **tick 差值**运算，与 `TICKS_PER_SEC` 无关 ✅；`SecToTicks`/`TicksToSec` 也精确（分别 = `s*f` 与 `t/f`）✅；

### 4. 方案对比

| 方案                        | 做法                                                                                                                                                                                                                                 | 代价 / 风险                                                                                                                                                             |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A（推荐，与 C4 同手法）** | 在分支 ① 加**编译期断言** `(1000U % XC_CFG_TICKS_PER_SEC) == 0U`（负数组长度技巧，0 运行时代价），并在 `Docs/XC_Config.md` / `Docs/XCOS.md` 写明"支持频率表"（1/2/4/5/8/10/20/25/40/50/100/125/200/250/500/1000 Hz；>1000 Hz 任意） | 编译期 +0；**破坏性**：现有 800/600 Hz 配置需改（推荐改用 1000 或 500）                                                                                                 |

| C                           | 改实现为**精确换算**（如 `TicksToMs(t) = (t * 1000U) / f` 用 64 位中间量 + 统一取整规则）                                                                                                                                            | 任意频率正确；但 Cortex-M3 上 64 位乘除会引入 `__aeabi_uldivmod`（体积/周期开销），而 `XC_Time_GetMs()` 可能位于热路径 ⇒ 需权衡；也可仅提供可选宏 `XC_CFG_TICKS_EXACT` |
| D                           | 不改                                                                                                                                                                                                                                 | 保持现状                                                                                                                                                                |

### 5. 验证设计

* **反向测试（若采纳 A）**：`-DXC_CFG_TICKS_PER_SEC=800` ⇒ **编译报错**（断言命中）；`=1000 / 500 / 250 / 2000 / 3000` ⇒ 编译通过 ✅；

* **回归**：现有三套用例 + MDK 全量重建（断言 0 体积影响）与仿真语义测点。

### A16 `>1000 Hz` 分支换算量级错误

**状态**：✅ **已修复（2026-09-14）** —— 分支 ② 的 4 个换算宏按 us 中间量重写（纯整数；探针 + 端到端实测通过）

**证据**（`Code/Inc/Internal/XC_TimeInternal.h:56-68`，分支 ②）

```c
#define XC_TICK_PERIOD_US        (1000000U / XC_CFG_TICKS_PER_SEC)
#define XC_Time_UsToTicks(Time)  (((Time) + XC_TICK_PERIOD_US - 1U) / XC_TICK_PERIOD_US) /* ✅ 正确 */
#define XC_Time_MsToTicks(Time)  ((Time) * XC_CFG_TICKS_PER_SEC)                         /* ✗ 应为 ms*f/1000 */
#define XC_Time_SecToTicks(Time) (XC_Time_MsToTicks(Time) * 1000U)                       /* ✗ 应为 s*f */
#define XC_Time_TicksToUs(Tick)  ((Tick) * XC_TICK_PERIOD_US)                           /* ✅ 正确 */
#define XC_Time_TicksToMs(Tick)  ((Tick) / XC_CFG_TICKS_PER_SEC)                        /* ✗ t<f 时恒 0 */
#define XC_Time_TicksToSec(Tick) (XC_Time_TicksToMs(Tick) / 1000U)                       /* ✗ 同源 */
```

**探针实测**（宿主 gcc，`XCOS.h` 展开宏后直接打印；同一份测点分别以不同 `f` 编译）

| `f` (Hz)     | `MsToTicks(1)` 实测 / 应为 | `SecToTicks(1)` 实测 / 应为 | `TicksToMs(1000)` 实测 / 应为 | `UsToTicks(1000)` | `TicksToUs(1000)` |
| ------------ | -------------------------- | --------------------------- | ----------------------------- | ----------------- | ----------------- |
| 1000（默认） | 1 / 1 ✅                   | 1000 / 1000 ✅              | 1000 / 1000 ✅                | 1 ✅              | 1 000 000 ✅      |
| 500          | 1 / 1 ✅                   | 500 / 500 ✅                | 2000 / 2000 ✅                | 1 ✅              | 2 000 000 ✅      |
| **2000**     | **2000** / 2 ✗            | **2 000 000** / 2000 ✗     | **0** / 500 ✗                | 2 ✅              | 500 000 ✅        |
| **4000**     | **4000** / 4 ✗            | **4 000 000** / 4000 ✗     | **0** / 250 ✗                | 4 ✅              | 250 000 ✅        |
| **10000**    | **10000** / 10 ✗          | **10 000 000** / 10000 ✗   | **0** / 100 ✗                | 10 ✅             | 100 000 ✅        |

**后果**

1. **延时/超时被放大 1000 倍**：`XC_Cor_DelayMs(1)`/`WaitNotifyMs`/`TimerSetMs`/`BlockDelayMs` 在 2000 Hz 下 ⇒ **2000 tick ≈ 1 s**（请求 1 ms，实际约 1000 ms）；
2. `XC_Time_GetMs()`/`TicksToMs()` 在"已运行 tick < f"期间**恒为 0**（2000 Hz ⇒ 前 1 秒一直报 0 ms），之后以 f ticks 为量化单位 ⇒ 误差可达 1 秒；
3. `UsToTicks`/`TicksToUs` 是该分支中**唯一正确**的两个（按 `TICK_PERIOD_US` 换算）。

**修法（建议；与分支 ① 的取整语义一致：时间→Tick 向上取整，Tick→时间 向下取整）**

```c
#define XC_Time_MsToTicks(Time)  ((((Time) * 1000U) + XC_TICK_PERIOD_US - 1U) / XC_TICK_PERIOD_US)
#define XC_Time_SecToTicks(Time) ((Time) * XC_CFG_TICKS_PER_SEC)        /* s ⇒ tick: 精确 */
#define XC_Time_TicksToMs(Tick)  (((Tick) * XC_TICK_PERIOD_US) / 1000U) /* tick ⇒ ms: 1 tick<1ms ⇒ 0 属精度下限 */
#define XC_Time_TicksToSec(Tick) (XC_Time_TicksToMs(Tick) / 1000U)
```

> 全程整数运算、无 64 位、无库调用；`TicksToMs` 在"1 tick < 1 ms"时仍可能得 0（那是精度下限，不再是量级错误；需要更细用 `TicksToUs`）。
> 溢出边界（`Time * 1000U` 在 ms 很大时）见 `Code/Inc/Internal/XC_TimeInternal.h` 注释里的取值上限说明。

**验证设计**

1. **探针（本条目已用）**：`f = 1000/2000/4000/10000` 打印上表 5 个宏 ⇒ 修复后应全部等于"应为"列；
2. **端到端（宿主 gcc）**：2000 Hz 下执行 `XC_Cor_DelayMs(1)` 后读 tick 数 ⇒ 期望 **2 tick**（现状 2000）；
3. **回归**：默认 1000 Hz 的三套用例 + MDK 全量重建/仿真（分支 ② 不参与默认构建 ⇒ 体积应无变化）。

**与 A12 的关系**：A12 处理"分支 ① 非 1000 因子频率的截断失真"（已用编译期断言收口）；本条是**分支 ② 的量级错误**，属独立缺陷（默认 1000 Hz 不触发）⇒ 独立条目。
