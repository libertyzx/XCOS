## 1. 根因（四处，前两处是主因）

1. **事件补偿路径未排除挂起任务**：`XC_Sch.c` 的 `XC_Sch_EventSched` 内局部宏 `WAKEUP_NOTIFY`（遍历时间表/溢出表/阻塞表）判据只有
   `NotifyState==WAIT && NotifyPending!=0`，**未排除** `TaskState==SUSPEND`；
   ⇒ 阻塞表中出现的"`SUSPEND` + 等待通知 + 未消费通知"任务会被移入就绪表、置 `READY`，**覆盖 `SUSPEND`**（挂起语义被破坏）。
2. **挂起不清通知**：`XC_Task_HandleSuspend` 只做"置 `SUSPEND` + 移入阻塞表"，`NotifyState`/`NotifyPending` 原样保留
   ⇒ 上述"僵尸组合"才可能出现（本缺陷另一半根因）。
3. **`SendNotify` 直接路径与 `Suspend` 的竞态窗口**（隐藏窗口）：`Suspend` 的状态写入**在锁外**，
   而 `SendNotify` 的"直接唤醒路径"（`Lock==0`）在锁内**未复核 `SUSPEND`**；
   ⇒ 中断在"判过 `TaskState != SUSPEND`"之后、任务上下文才完成挂起时，中断仍会把任务移入就绪表并置 `READY`。
4. **恢复不交付通知**：`XC_Task_Resume` 只"移表 + 置 `READY`"，若挂起前留有未消费通知，
   `NotifyState` 仍为 `WAIT` ⇒ 恢复后 `XC_Cor_IsNotifyTimeout()` **误报超时**（明明有通知却报超时）。

> 触发链（文档 A2 的时序）：任务 A `WaitNotify` → 锁窗口中断 `SendNotify`（只登记不移表）→ 另一任务 `Suspend(A)` → 主循环 `EventSched` 误唤醒 A。
> 关键点：`SendNotify` 对"发送时已挂起"的任务返回 `XC_FAIL`，本缺陷绕过它是因为**通知先于挂起**发生。

## 2. 修复（3 处，均为最小改动）

### 2.1 `Code/Src/XC_Sch.c`：`WAKEUP_NOTIFY` 追加"挂起不唤醒"

```c
/* 原判据(2 个条件) */
if((XC_LIST_TO_TCB(pIterator)->NotifyState == (uint8_t)XC_NOTIFY_WAIT) &&   /*是等待唤醒*/
   (XC_LIST_TO_TCB(pIterator)->NotifyPending != 0U)) {                      /*有待处理通知*/

/* 修复后(3 个条件; 宏续行符省略) */
if((XC_LIST_TO_TCB(pIterator)->NotifyState == (uint8_t)XC_NOTIFY_WAIT) &&   /*是等待唤醒*/
   (XC_LIST_TO_TCB(pIterator)->NotifyPending != 0U) &&                      /*有待处理通知*/
   (XC_LIST_TO_TCB(pIterator)->TaskState != (uint8_t)XC_TASK_SUSPEND)) {    /*挂起优先级最高: 不唤醒挂起任务*/
```

配套必须改注释：`XC_Sch.c` 中该宏的说明块（现写着"**已知缺陷(使用注意)**……框架暂不处理"）须改写为
"**挂起优先级最高（A2 已修复）**：唤醒条件已排除 `SUSPEND`；挂起前登记的待处理标志保留在 TCB 中，由 `XC_Task_Resume` 恢复时交付"。
**若不同步改写，后续读者会以为该误唤醒行为仍被接受。**

### 2.2 `Code/Src/XC_Task.c`：`XC_Task_Resume` 在锁内交付挂起期通知

```c
XC_Core_Lock(phTCB->phXCOS);    // 锁
XC_Task_MoveToReadyList(phTCB); // 将任务移动到就绪表
/* 挂起期间已登记的通知(待处理标志)在恢复时交付: 消费标志并置"通知唤醒",
 * 否则恢复后 XC_Cor_IsNotifyTimeout() 会因 NotifyState 仍为 WAIT 而误报超时 */
if((phTCB->NotifyState == (uint8_t)XC_NOTIFY_WAIT) && (phTCB->NotifyPending != 0U)) {
    phTCB->NotifyPending = 0U;                        // 消费:清待处理标志(常量0写)
    phTCB->NotifyState   = (uint8_t)XC_NOTIFY_WAKEUP; // 交付:通知唤醒(等待侧视为"已通知")
}
XC_Core_Unlock(phTCB->phXCOS);  // 解锁
phTCB->TaskState = XC_TASK_READY; // 任务状态:就绪
```

### 2.3 `Code/Src/XC_Task.c`：`XC_Task_HandleSuspend` 把状态写入移入锁内

```c
void XC_Task_HandleSuspend(XC_TaskHandle_t phTCB)
{
    XC_Core_Lock(phTCB->phXCOS);        // 锁(状态写与移表同锁域: 防中断并发覆盖)
    phTCB->TaskState = XC_TASK_SUSPEND; // 任务状态:挂起(优先级最高: 任何唤醒路径见此值均不移表)
    XC_Task_MoveToBlockedList(phTCB);   // 将任务移动到阻塞表
    XC_Core_Unlock(phTCB->phXCOS);      // 解锁
}
```

> **为什么 2.3 是必需的**：它把"状态写入"与"移表"放进同一锁域，使 `SendNotify` 的临界区与挂起动作**串行化**，
> 结构上消除 §1.3 的竞态窗口。若坚持保留"锁外写状态"的写法，则必须在 `SendNotify` 的直接路径**锁内补一次 `SUSPEND` 复核**
> （`if(TaskState == SUSPEND) { Unlock; return XC_CONTINUE; }`），且该复核只能"事后补救"，不如 2.3 直接。
> 两处同时加并不冲突，但**不必要**（2.3 已覆盖）。

## 3. 修复后的不变量（本方案的核心语义）

> **`TaskState == SUSPEND` ⇒ 任何唤醒路径（时间表超时 / 溢出表 / 事件补偿）都不移表、不改状态；**
> **挂起只能由 `XC_Task_Resume` 解除；`Resume` 负责交付挂起前已登记的通知；挂起期间的新通知一律 `XC_FAIL`（不登记、不覆盖 `pNotifyData`）。**

派生结论：
1. 挂起任务被恢复后，等待侧（`XC_Cor_WaitNotify`）的分支取值：
   **挂起前有未消费通知 → "已通知"**（`IsNotifyTimeout()==0`，`GetNotifyData()` 有效）；
   **无未消费通知 → "未通知（超时分支）"**（`IsNotifyTimeout()==1`，用户按"没等到通知"处理即可，**不会死等**）；
2. 挂起优先级高于"通知/超时/延时"等一切阻塞原因 —— 与既有文档"挂起可以覆盖任务的所有阻塞状态，优先级最高"一致，本方案把这句话**落到判据上**；
3. `NotifyPending` 的 SPSC 契约不变（生产侧只写常量 1、消费侧只写常量 0）。

## 6. 边界（本方案**不**改变的行为）

* **挂起期间到达的新通知仍一律拒绝**（`SendNotify` 立即 `XC_FAIL`，不登记、不覆盖 `pNotifyData`）—— 既有"挂起任务不可通知"语义；若要改为"挂起期登记、恢复时交付"，需在 `SendNotify` 的 `SUSPEND` 早退分支上**另行决策**（会放宽现有 SPSC 时序假设）；
* `NotifyPending` 仍为 **SPSC**（单生产者单消费者）；多生产者需用户自行加锁；
* 已超时/已离开等待的通知不会被"补发"（既有语义）。
