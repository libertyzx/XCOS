## 1. 背景：为什么要改成单标志

### 1.1 现状机理（A1）
```c
/* XC_Task.c:550 / 559 / 562 */
if((phTCB->NotifyProduced + 1U) != phTCB->NotifyConsumed) { phTCB->NotifyProduced++; }
```
`NotifyProduced` 是 `uint8_t`，`+ 1U` 后**提升为 `int`**，"留一格判满"所需的**模 256 语义丢失**：

| 状态（`P=255, C=0`） | 表达式 | 判定 | 结果 |
| --- | --- | --- | --- |
| 设计意图 | `(255+1) mod 256 = 0 == C` | 满 ⇒ 丢弃 | ✅ |
| 实际计算 | `255+1U = 256 != 0` | 误判"未满" ⇒ 自增 | ❌ 回绕：`P` 变 0 == `C` ⇒ **"有通知"变成"没有通知"** |

* **触发条件（经仿真实测修正）**：需**同时**满足 —— ①`P == 255` 时判满误判（`P + 1U` 提升为 `int` 得 `256`，与任何 `C` 都不等）⇒ 自增 ⇒ `P` 回绕成 0；**只有 `C == 0` 时**回绕才造成 `P == C`（记录被抹），`C ≠ 0` 时差值不变、**无可观测影响**；②未被消费的发送次数恰为 **256 的整数倍**（回绕后任何一次新发送都会把差值恢复成非零）。⇒ 即"`Consumed == 0` **且** 未消费量 ≡ 0 (mod 256)"，而非"发送总量"或"跨过 255"。
* **可达性**（通读全部代码 + **仿真实测**复核）：`XC_Task.c:550`（非等待分支）**可达**——仿真已复现（256/512 次发送 ⇒ 该次等待误阻塞）；`:559`（等待+锁窗口，仅中断）**可达**且最严重（唯一唤醒凭据被抹，`EventSched` 跑到也扫不醒 ⇒ `WaitNotify(0)` 永久睡眠）；`:562`（事件计数）**不可达**（主循环每轮 drain）。
* **后果**：偶发多阻塞一次 / 偶发永久丢唤醒；触发约 1/256 量级且依赖时序，**静默无告警**（仿真对照见 §6.2）。

### 1.2 为什么"双计数"不是更安全（模型不匹配）
* 双计数**不是冗余备份**：`P`、`C` 单独都没有意义，只有差值有意义 ⇒ 一端出错即**错误决策**、且无法自检；
* 它的"稳"来自"**每字段单写者**"，而这是**用户可违反**的纪律（文档要求"多生产者需加锁"；框架自己的 `XC_Task_ClrNotify()` 又是任意上下文可调用的用户 API）；
* XCOS 的通知语义是**单槽"有没有"**：`WaitNotify` 只返回布尔、`pNotifyData` 会被后写覆盖、消费是**一次性全清**（`C = P`）⇒ **计数能力从未被使用**；
* ⇒ 把"布尔"做成"带边界的计数"，凭空引入唯一那条静默失效路径。**模型匹配需求才最安全**。

### 1.3 单标志为什么在本框架下成立
| 关注点 | 结论（详见评审附录 A.2/A.3/A.6） |
| --- | --- |
| 原子性 | 生产侧 `= 1U`、消费侧 `= 0U`，**都是常量写**（无 `++`/`\|=` ⇒ **无 RMW**）；只要求"对齐单字节 `volatile` 存取不被撕裂"——**现状已依赖同一前提**（计数就在 TCB 偏移 34/35 相邻字节） |
| 实测指令 | `MOVS r1,#1` + **`STRB r1,[r0,#0]`**（AC5 `-O1/-O3/-Ospace`、armclang/AC6 `-O2` 一致）⇒ **内存访问仅 1 条**，中断无法落在"半写"中间 |
| 竞态 | 两个写者写集合互斥（{1} vs {0}），任一交错结果只可能是 0/1，且**两种结果协议都安全**（`WAIT` 先置 → 查标志；否则走唤醒路径） |
| 多生产者 | 写同值 `1` **幂等**（现状两个 `Produced++` 是丢更新的 RMW）⇒ 要求更低 |
| 回绕/边界 | **不存在**（布尔） |

## 2. 改造模型（新协议）

```c
/* 字段 */
volatile uint8_t NotifyPending;   /* TCB : 1=有未消费通知, 0=无          */
volatile uint8_t EventPending;    /* XCOS: 1=有待落地的异步调度事件, 0=无 */

/* 生产侧（任务或中断）—— 只写常量 1 */
phTCB->pNotifyData   = pNotifyData;   /* ① 先写数据(保证"看到标志即看到最新数据") */
phTCB->NotifyPending = 1U;            /* ② 再置标志(无条件, 无判满, 幂等)          */
if(异步登记需要) { phXCOS->EventPending = 1U; }

/* 消费侧（等待处理）—— 顺序不可变: 先置 WAIT, 再查标志 */
phTCB->NotifyState = WAIT;
if(phTCB->NotifyPending != 0U) { phTCB->NotifyPending = 0U; /* 消费, 不阻塞 */ }
else                            { BLOCKED + 入表; }

/* 唤醒侧（事件调度）—— 先清后处理, 不丢 */
if(phXCOS->EventPending != 0U) { phXCOS->EventPending = 0U; XC_Sch_EventSched(phXCOS); }
/* 扫到 WAIT 任务时: if(NotifyState==WAIT && NotifyPending!=0) { NotifyPending = 0U; 搬就绪表; } */
```

**必须遵守的纪律**（写入代码注释，评审 A.6）
1. **只允许常量写**：`= 1U` / `= 0U`；**严禁** `|=`、`++`、`&=`（会退化成 RMW）；
2. 字段必须 `volatile`；
3. **数据先写、标志后置**；
4. 消费侧**先置 `WAIT`、再查标志**；
5. 不用位域承载标志（位域会生成"读-改-写"，可被中断且连带改同单元其它位）。

## 4. 逐文件改动（before → after）

### 4.1 `Code/Inc/Internal/XC_TypeInternal.h`

**TCB（`struct XC_TaskCB_tag`，偏移 34）**
```c
/* before */
volatile uint8_t NotifyProduced; // 通知-生产者
volatile uint8_t NotifyConsumed; // 通知-消费者

/* after */
/**
 * 框架的通知使用"待处理标志"实现(替代原"生产者/消费者"计数对);
 * - 生产侧(任务或中断)只写常量 1,消费侧(等待处理/事件调度/复位)只写常量 0;
 * - 两侧都不做"读-改-写" => 单生产者单消费者(SPSC)下天然安全,无需原子操作/关中断;
 * - 单字节 volatile:写入即整体生效,不存在"计数回绕/判满"边界(原计数实现曾因此丢唤醒);
 * - 纪律:严禁 "|="、"++"、位域 等写法(会退化成读-改-写);
 */
volatile uint8_t NotifyPending; // 通知-待处理(1:有未消费通知;0:无)
```

**`struct XCOS_tag`（偏移 38）**
```c
/* before */
volatile uint8_t EventProduced; // 事件-生产者(用于通知操作触发)
volatile uint8_t EventConsumed; // 事件-消费者(用于通知异步操作触发后处理)

/* after */
/**
 * 异步调度事件-待处理标志 ...
 */
volatile uint8_t EventPending; // 异步调度事件-待处理(1:需要事件调度;0:无)
```
另：`TCB` 字段说明列表、字节数说明同步更新；**偏移布局不变**（`NotifyPending` 占偏移 34，偏移 35 转为对齐 padding；`Lock` 仍在 `XCOS_t` 偏移 37，`EventPending` 占 38，偏移 39 转为 padding）。

### 4.2 `Code/Inc/XC_Task.h`（`XC_Task_ClrNotify`）
```c
/* before */ (phTCB)->NotifyConsumed = (phTCB)->NotifyProduced;
/* after  */ (phTCB)->NotifyPending  = 0U;   /* 并补充"须在主循环(目标任务自身)调用"的上下文约定 */
```

### 4.3 `Code/Inc/XC_Cor.h`（`XC_Cor_ClrNotify`）
```c
/* before */ phXCCorTCB->NotifyConsumed = phXCCorTCB->NotifyProduced;
/* after  */ phXCCorTCB->NotifyPending  = 0U;
```

### 4.4 `Code/Src/XC_Task.c`

**(a) `XC_Task_BasicInit`**
```c
/* before */ phTCB->NotifyConsumed = phTCB->NotifyProduced;
/* after  */ phTCB->NotifyPending  = 0U;   /* 语义等价: "差值归零" == "标志清零" */
```

**(b) `XC_Task_HandleWaitNotify`（消费侧，顺序不可变：先置 `WAIT`，再查标志）**
```c
/* before */
if(phTCB->NotifyProduced != phTCB->NotifyConsumed) {
    phTCB->NotifyConsumed = phTCB->NotifyProduced;
    ...
/* after  */
if(phTCB->NotifyPending != 0U) {
    phTCB->NotifyPending = 0U;
    ...
```
（`else` 分支 `BLOCKED + HandleBlocking` 与其"隐式解锁"契约均未改动。）

**(c) `XC_Task_SendNotify`（生产侧：删除两处"判满"，改为无条件置位）**
```c
/* before */
phTCB->pNotifyData = pNotifyData;
if(phTCB->NotifyState != (uint8_t)XC_NOTIFY_WAIT) {
    if((phTCB->NotifyProduced + 1U) != phTCB->NotifyConsumed) { phTCB->NotifyProduced++; }
    return (XC_CONTINUE);
}
if(XC_Core_GetLockState(phTCB->phXCOS)) {
    if((phTCB->NotifyProduced + 1U) != phTCB->NotifyConsumed) { phTCB->NotifyProduced++; }
    if((phTCB->phXCOS->EventProduced + 1U) != phTCB->phXCOS->EventConsumed) { phTCB->phXCOS->EventProduced++; }
    return (XC_CONTINUE);
}

/* after */
phTCB->pNotifyData   = pNotifyData;   /* ① 先写数据 */
phTCB->NotifyPending = 1U;            /* ② 再置标志(常量1写,无条件/幂等/无读改写) */
if(phTCB->NotifyState != (uint8_t)XC_NOTIFY_WAIT) {
    return (XC_CONTINUE);             /* 只记录;等待侧会先置 WAIT 再查标志 => 不会漏 */
}
if(XC_Core_GetLockState(phTCB->phXCOS)) {
    phTCB->phXCOS->EventPending = 1U; /* 异步: 仅登记事件 */
    return (XC_CONTINUE);
}
```
（"调度未运行"的直接路径 `Lock → MoveToReadyList → Unlock → WAKEUP/READY` 未改动。）

### 4.5 `Code/Src/XC_Sch.c`

**(a) `XC_Sch_Init`**
```c
/* before */ phXCOS->EventProduced = 0U; phXCOS->EventConsumed = 0U;
/* after  */ phXCOS->EventPending  = 0U;
```

**(b) `XC_Sch_Start` 事件门控（先清后处理）**
```c
/* before */
Trigger = phXCOS->EventProduced;
if(Trigger != phXCOS->EventConsumed) {
    phXCOS->EventConsumed = Trigger;
    XC_Sch_EventSched(phXCOS);
}
/* after  */
if(phXCOS->EventPending != 0U) {
    phXCOS->EventPending = 0U;      /* 先清: 处理期间再置位 => 下轮再处理,不丢事件 */
    XC_Sch_EventSched(phXCOS);
}
```
（局部变量 `uint8_t Trigger;` 随删除，避免 `-Wunused-but-set-variable`。）

**(c) `WAKEUP_NOTIFY` 唤醒判据/消费**
```c
/* before */
(XC_LIST_TO_TCB(pIterator)->NotifyState == (uint8_t)XC_NOTIFY_WAIT) &&
(XC_LIST_TO_TCB(pIterator)->NotifyProduced != XC_LIST_TO_TCB(pIterator)->NotifyConsumed)
    ...
    XC_LIST_TO_TCB(pIterator)->NotifyConsumed = XC_LIST_TO_TCB(pIterator)->NotifyProduced;
/* after  */
(XC_LIST_TO_TCB(pIterator)->NotifyState == (uint8_t)XC_NOTIFY_WAIT) &&
(XC_LIST_TO_TCB(pIterator)->NotifyPending != 0U)
    ...
    XC_LIST_TO_TCB(pIterator)->NotifyPending = 0U;
```

| --- | --- | --- | --- |
| 提前通知（先发后等） | `WaitNotify` 不阻塞 | 同 | ✅ |

| `Reset` / `Remove` / `Reg` / `Add` | `BasicInit` 清空差值 | `BasicInit` 清 0 | ✅ |

| 挂起任务发送通知 | `XC_FAIL`（**先于**任何记录） | 同 | ✅ |
| 事件补偿（锁窗口登记 → 主循环扫描） | `EventProduced/Consumed` | `EventPending`（先清后处理） | ✅ |

| `sizeof(XC_TaskCB_t)` / `sizeof(XCOS_t)` | 44 / 44 | 44 / 44 | ✅ |

## 9. 多中断 / 抢占场景分析（含 `XCOS_t.EventProduced/EventConsumed` 的决策记录）

### 9.0 先明确模型分层（重要澄清，2026-09-14）
`SPSC` 只描述**任务级通知**；在**框架级**，生产者是"所有中断"、消费者是"主循环" ⇒ 模型不同，**必须分开论证**：

| 层级 | 共享对象 | 并发模型 | 谁写 / 谁读 | 为什么安全 |
| --- | --- | --- | --- | --- |
| 任务级通知 | `TCB.NotifyPending` | **SPSC**（1 生产者 × 1 消费者） | 生产者=某一个中断或任务（只写 1）；消费者=目标任务自身（只写 0） | 两侧只写常量；即使"多个中断通知同一任务"（违反约定）也只是**写同值 1 ⇒ 幂等** |
| 任务级数据 | `TCB.pNotifyData` | 同上（**由用户保证单生产者**） | 生产者写、目标任务读 | 字对齐写原子；同一任务多生产者 ⇒ "最后写入胜出"（契约） |
| 框架级事件门控 | `XCOS_t.EventPending` | **MPSC**（N 生产者 × 1 消费者） | 生产者=**所有中断**（只写 1）；消费者=主循环（只写 0） | **所有写者写同一常量 1** ⇒ 无丢更新；门控"先清后处理" + 扫描穷尽 ⇒ 不漏 |
| 框架级临界区 | `XCOS_t.Lock` + 四张链表 | **串行化访问**（非无锁） | 主循环持锁原子区；中断仅在"读到 0"时获取并**配对释放** | 抢占嵌套的中断看到 `Lock==1` ⇒ 只登记，**不解锁他人锁、不动表** |

**关键澄清**：原实现用 `EventProduced++`，而该字段的写者是**所有中断** —— 框架级本来就是 **MPSC**，`++` 又是"读-改-写" ⇒ 在 MPSC 下**必然存在丢更新竞争**（框架无法替多个中断做序列化）。旧实现之所以未暴露，**仅因为门控只要求"非零"**（丢一次增量仍非零，扫描照样触发）。
⇒ 本次改造把框架级从"**MPSC 下不安全的计数**"提升为"**MPSC 下安全的常量标志**"，这是 §9.4 建议改 `EventPending` 的**最强理由**。

### 9.1 问题
多个中断都可能调用 `XC_Task_SendNotify`，中断之间可以**抢占（嵌套）**，被通知的任务**各不相同**。单标志够用吗？

### 9.2 结论：够用（逐共享对象分析）

| 共享对象 | 写者 | 抢占/嵌套下是否安全 | 理由 |
| --- | --- | --- | --- |
| `TCB.NotifyPending` | 该任务的"通知者"（可能是若干不同 ISR 之一） | ✅ | 每任务各占**独立字节**，互不相干；写的都是**常量 1**（幂等） |
| `TCB.pNotifyData` | 同上 | ⚠️ 用户契约 | **同一任务**被两个 ISR 通知 ⇒ 指针竞写（字对齐写原子，但"最后一次胜出"）；**不同任务** ⇒ 完全无冲突 |
| `XCOS_t.EventPending` | **所有** ISR（主循环只读/清 0） | ✅ | **所有写者都写同一个常量 1** ⇒ 任一交错结果都是 1，**不存在"丢更新"** |
| 四张链表 | ISR 仅在 `Lock==0` 时写（直接路径） | ✅ | `Lock==1` ⇒ ISR 只登记（异步分支）；**抢占的 ISR 看到 `Lock==1` 不会去解锁别人的锁** |
| `Lock` | 主循环 + ISR 直接路径 | ✅（本次未改其契约） | ISR 只在"先读到 0"时才置 1 并配对释放；嵌套 ISR 一律走异步分支 |

### 9.3 "不会丢"的证明骨架（三条不变量）
1. **门控是"有/无"语义 + 先清后处理**：`if(EventPending != 0U){ EventPending = 0U; XC_Sch_EventSched(); }`
   ⇒ 扫描期间（或扫描前一刻）的任何新增登记都会把标志**再次置 1** ⇒ 下一轮必然再扫一次；
2. **扫描穷尽且幂等**：一次扫描遍历时间表/溢出表/阻塞表，唤醒**所有** `WAIT ∧ NotifyPending != 0` 的任务
   ⇒ N 个中断登记 N 个不同任务，**一次扫描全部处理**，不需要"计数"；
3. **扫描游标之后登记的也不会漏**：该任务的 `NotifyPending` 与 `EventPending` 同时被置 1 ⇒ 下一轮补扫。

> 因此 `EventPending` **不需要**表达"有几个登记"——消费者的动作是"**把该做的都做一遍**"，而不是"做 N 次"。这也正是原 `EventProduced/EventConsumed` 计数对**从未被真正使用**的能力（原门控 `Trigger=P; C=Trigger;` 本身就是"非零"语义）。

### 9.4 `XCOS_t.EventProduced/EventConsumed` 是否必须改？——决策记录
**必须性**：**不是**"修可复现缺陷"级别（该计数回绕在工程上不可达，见评审 §A1 逐站点表），但**建议改**，理由三条：

1. **模型一致性**：通知侧已是标志，事件侧若保留计数，框架内同时存在两套模型（维护/评审成本上升）；
2. **去掉 ISR 中的 RMW**：`EventProduced++` 是"读-改-写"，在**多中断嵌套**下属于"丢更新"竞争（虽然门控只要"非零"，实践中无害）；改为常量写后**该竞争彻底消失**，且 ISR 路径从 5~6 条降为 1 条 `store`；
3. **去掉最后一处"判满"写法**（原 `XC_Task.c:562`）：框架内不再存在"留一格判满 + 整型提升"的写法，杜绝后人模仿。

**若选择回退**（保留 `EventProduced/EventConsumed`）：功能上仍可用（门控语义等价），但需接受三点——ISR 路径仍多 5~6 条指令、保留一处 RMW 竞争、保留一处判满写法、以及"通知=标志 / 事件=计数"的模型分裂。回退仅涉及三处：`XC_TypeInternal.h`（`XCOS_t`）、`XC_Sch.c`（`XC_Sch_Init` + 主循环门控）、`XC_Task.c`（`SendNotify` 异步分支）。

### 9.5 多中断场景下的**真实残余风险**（与本次改动无关）

| 风险 | 说明 | 归属 |
| --- | --- | --- |
| 中断中调用"会移表"的 API | `Suspend/Resume/Reset/Remove` 在中断中会 `Lock/Unlock` 并移表；**嵌套中断**下"提前解锁"风险更高 | 需上下文断言 / 登记式 API（评审记录，2026-09-14） |
| 同一任务被多个中断通知 | `pNotifyData` 竞写（框架只保证"最后写入胜出"） | 文档契约：每任务单生产者；若必须多生产者，需为数据指针增加"每源独立槽"（框架外扩展） |
| 重排序/多核 CPU | 仍需用户在数据与标志之间加屏障 | 框架既有声明（`XC_Task.c` 通知段头注释） |
