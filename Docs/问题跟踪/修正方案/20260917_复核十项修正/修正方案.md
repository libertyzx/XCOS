## 2. 为什么这么做（关键取舍）

1. **A19 只动"更新时机"，不动判定式**：`PrevTick > Tick` 的语义没变（⇔ 相邻两次观察之间发生过回绕），只是把"观察"从"偶发"变成"每轮"；
   备选"用溢出表首节点反推回绕"需要引入新的不变量与状态，风险更大且更难验证。
2. **B5 容忍值取 1 而不是"放宽为 ≤1"**：任务上下文下"计数虚高 1"仍会被抓到（差值变 2）；盲区只剩"非任务上下文 + 恰好差 1"。
3. **A22 只清 `XC_Task_Reg` 的帧栈，不动 `XC_Task_Add`**：分步注册允许"先 `XC_Task_SetCorStack` 再 `Add`" ⇒ 清空会抹掉用户配置（那是**真回归**）；因此 `Add` 路径以**文档契约**收口。
4. **C5 选"删掉配置入口"而非"保留宏 + 收紧断言"**：宏名留着就是在宣传"可以配 Tick 宽度"，而答案是"只有 32 位能活"；
   既然不可配置，`== 4U` 断言也永远不会失败 ⇒ 一并删除（改宽度只能改 `typedef`，那是**改框架**、不是配置）；
   类型定义同时从配置头搬到类型层（`Internal/XC_TypeInternal.h`），配置头只留配置。仓内无工程使用该宏 ⇒ 兼容成本近 0。
5. **`#9` 不新增第 3 个状态**：新增 `RESUMED` 会让"被恢复"看起来像"收到通知"（对只判断 `IsNotifyTimeout()` 的应用更危险）；改文档是代价最小且不改变行为的处置。
