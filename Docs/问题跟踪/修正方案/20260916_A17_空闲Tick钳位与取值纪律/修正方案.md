## 1. 问题

### 1.1 现状代码（`XC_Sch.c` 第 313~334 行）

```c
313  // 判断就绪表是否有任务(空闲处理)
314  if((XC_List_ListValid(&phXCOS->ReadyList) == 0) && (phXCOS->fIdle != NULL)) {
         /* ... 原有 4 分支说明注释 ... */
323      Tick = XC_Time_GetTick();                       // ① 锁外读"当前 Tick"
324      if(XC_List_ListValid(&phXCOS->TimeList)) {        // ② 锁外判"时间表非空"(快照)
325          Tick = XC_Sch_GetNextTaskWakeupTick() - Tick; // ③ 再取首节点 + 无符号减法
         }
327      else if(XC_List_ListValid(&phXCOS->TimeOverflowList)) {   // ④ 溢出表同理
328          Tick = XC_LIST_TO_TCB(XC_List_GetListStartNode(&phXCOS->TimeOverflowList))->TaskWakeupTick - Tick;
         }
330      else {
331          Tick = ~0U;                                   // ⑤ 两表皆空: 按最大时间休眠(合法语义, 保留)
         }
333      phXCOS->fIdle(phXCOS, Tick);                      // 交给用户
334  }
```

**三重隐患（①②③步都在"未持锁、未关中断"的自由窗口里）**：

| 隐患 | 机理 | 结果 |
| --- | --- | --- |
| **① 下溢** | ①③之间 Tick 前进(定时器 ISR) ⇒ `首节点唤醒时刻 − 当前 Tick < 0` ⇒ `uint32` 回绕 | `IdleTick = 0xFFFFFFFF`（≈49.7 天），语义应为 **0（别睡）** |
| **② 陈旧快照** | ②判"非空"之后、③取首节点之前，ISR 走 `SendNotify` 的**直接搬表**路径把节点搬走（`XC_Task.c:636-641`）；若搬空 ⇒ ③对**表根**做 `XC_LIST_TO_TCB`（= 指针强转，`ListNode` 是 TCB 首成员） | 读到 `&XCOS_t + 28` = **`BlockedList.pPrev`**（RAM 指针）⇒ `IdleTick ≈ 0x2000_xxxx` |
| **③ 窗口内回绕** | ①之后 Tick 回绕（49.7 天一次）⇒ 时间表项全部"已过期"但尚未换表 | `IdleTick ≈ 一个整回绕` |

### 1.2 三条失败时序（`T0` = `TimeSched` 内部第 93 行读到的 Tick）

```
【A】下溢（最常见）
T0 │ TimeSched 读 T0；首节点 W=T0+1(未到) ⇒ 留表
   │ TimeSched 尾部 + EventSched(遍历 3 表) + 两次判断 —— 期间定时器 ISR 走了 ≥2 个 tick
①  │ 读 Tick = T0+2
③  │ IdleTick = (T0+1) − (T0+2) = −1 ⇒ 0xFFFFFFFF   ← fIdle 被要求"睡 49.7 天"

【B】陈旧快照（把"表根"当任务读）
② │ 判"时间表非空" ⇒ true（表内仅 1 个"等待通知+带超时"任务）
   │ ISR: SendNotify(该任务) ⇒ Lock=0 直接搬表(摘出时间表→插就绪表尾) ⇒ 时间表变空
③ │ XC_Sch_GetNextTaskWakeupTick() ⇒ 对表根做 container_of ⇒ 读 BlockedList.pPrev
   ⇒ IdleTick ≈ 0x2000_1A2C(≈5.4 亿 tick ≈ 6 天@1kHz)

【C】窗口内回绕（极罕见）
T0 │ TimeSched 读 T0(回绕前, 巨大)，首节点 W∈(T0,0xFFFFFFFF]，判"未到"
   │ 窗口内 Tick 回绕 ⇒ 现在是小值(=那批任务其实已到期, 等下一轮换表)
③ │ IdleTick = W − 小值 ≈ 0xFFFFFExx(≈ 一个整回绕)
```

### 1.3 为什么"正常路径"不会错（不变式，也是本方案的护栏）

1. 第 314 行"就绪表为空"⇒ **`TimeSched` 本轮没唤醒任何任务**（`EventSched` 只往就绪表**加**）⇒ 时间表所有节点满足 `唤醒时刻 > T0`；
2. ⇒ 只要"读 Tick 到取节点之间 Tick 不前进、且表不被改动"，差值必 ≥0 —— 而**这两条都没有机制保证**（定时器 ISR 独立前进、ISR 可直接搬表）；
3. `~0U`（两表皆空）是**有意**语义（无待唤醒任务 ⇒ 可长睡），**保留不变**。

## 2. 影响与可达性

### 2.1 触发三要素（同时成立才出问题）

| # | 条件 | 说明 |
| --- | --- | --- |
| (i) | **就绪表为空** | 否则整个空闲分支不执行（第 314 行） |
| (ii) | **最早唤醒时刻恰在 1 个 tick 内**（`W = T0+1`） | 由 §1.3 不变式推出：就绪表为空 ⇒ `W > T0` ⇒ 要"已过点"只能是 `W = T0+1`；⇒ 高频短延时（`DelayUs`/`DelayTick(1)`/1-tick 超时）场合最易满足 |
| (iii) | **窗口内 Tick 前进 ≥2**（或窗口内回绕 / ISR 命中那十几条指令） | 见下表（与 `XC_CFG_TICKS_PER_SEC` 强相关） |

### 2.2 与 Tick 频率的关系（窗口 ≈ `TimeSched` 尾部 + `EventSched` 3 表遍历 + 两次判断）

| `XC_CFG_TICKS_PER_SEC` | 2 个 tick 的周期数（@72 MHz） | 窗口能否达标 | 结论 |
| --- | --- | --- | --- |
| **1 kHz**（默认） | 144 000（2 ms） | 需上百节点遍历（`TaskNum` 上限 255，`EventSched` 每节点约几十~200 周期）⇒ 仍差一个量级 | **近似不可达**（默认档风险可忽略） |
| **10 kHz** | 14 400（200 µs） | 几十个节点即可越过 | **可达** |
| **100 kHz** | 1 440（20 µs） | 十几个节点即可越过 | **易命中** |

> 隐患②（陈旧快照）**与 Tick 频率无关**：只要 ISR 命中那"十几条指令"的窗口即可；而该窗口**每轮空闲都会经过**（空闲系统每秒数千次）⇒ 不能按"亿分之一"估。

### 2.3 后果分级（取决于用户 `fIdle` 如何用这个值；框架契约要求用户"按它行动"）

| `fIdle` 写法 | 后果 | 是否受影响 |
| --- | --- | --- |
| `__WFI()`（示例工程 `Idle()`，不用提示值） | 基本无害 | ❌ 不受影响 |
| 按提示值进低功耗 + Tick 停走 | **设备假死**（睡 ≈49.7 天；WDT 关掉 = 变砖级） | ✅ 严重 |
| 按契约注释 `TickSet(GetTick() + IdleTick)` 回填 | 时钟跳变 ⇒ 时间调度"整表回绕处理" ⇒ **延时任务被集体提前唤醒**一次 | ✅ 中 |
| 用提示值做负载统计/日志 | 统计被污染 | ✅ 轻 |

## 3. 方案设计

### 3.1 目标与新的语义契约（先把"值域"定义死）

| `IdleTick` 取值 | 含义（**新契约**） |
| --- | --- |
| `0` | **不要休眠**：此刻有"已到点/待处理"的工作（也已覆盖①下溢、②竞态、③回绕三种异常） ⇒ 立刻回主循环 |
| `1 … 0xFFFFFFFE` | **建议休眠上限**：距下一个任务唤醒还有这么多 tick |
| `~0U`（`0xFFFFFFFF`） | **无待唤醒任务**（时间表与溢出表都空）⇒ 按平台最大休眠能力处理（既有语义，保留） |

> 结论：`IdleTick = 0` 从"偶发（窗口刚好跨 1 tick）"变为"**稳定出现**" ⇒ 用户代码必须把 0 当正常值处理（示例工程不读该值，无影响）。

### 3.2 方案 A′（**未采用**，保留为对照）：指针捕获取值 + 钳位 + 就绪复检（**无需加锁**）

**改动点唯一**：`Code/Src/XC_Sch.c` 空闲分支内的取值/计算（≈22 行）+ 1 个局部变量 `XC_ListNode_t* pHead`。

```c
252      XC_DIAG_ASSERT(phXCOS != NULL);
253      XC_TaskHandle_t phTCB;
254      XC_ListNode_t*  pHead; // [A17] 空闲分支: 捕获的"表首节点"指针(非表根即有效)
255      XC_Tick_t       Tick;
...
323      Tick = XC_Time_GetTick(); // 得到当前Tick
324      /**
325       *  [A17] 取值纪律(钳位): 见 "XC_TypeInternal.h" 的 fIdle 契约 ——
326       *  - 先"捕获表首节点指针"再判有效性(等价 ListValid), 之后再**只对该节点**取值 ⇒
327       *    即使此刻中断把节点搬走("通知"直接唤醒路径), 读到的仍是该 TCB 的真实字段,
328       *    **不会**把"表根"当 TCB 读(读表根得到的是框架实例里的无关字节);
329       *  - Tick 前进(该唤醒时刻已过点) / 窗口内 Tick 回绕 ⇒ 一律给 0(**不要休眠**),
330       *    禁止让无符号减法回绕成 ~0xFFFFFFFF(≈49.7 天);
331       */
332      if(phXCOS->PrevTick > Tick) { // 窗口内 Tick 回绕(时间调度待处理)
333          Tick = 0U;
334      }
335      else if((pHead = XC_List_GetListStartNode(&phXCOS->TimeList)) != &phXCOS->TimeList) { // 时间表有节点
336          XC_Tick_t Next = XC_LIST_TO_TCB(pHead)->TaskWakeupTick; // 时间表首节点 = 最近唤醒时刻
337          Tick = (Next > Tick) ? (Next - Tick) : 0U;              // 已过点 ⇒ 0(不休眠)
338      }
339      else if((pHead = XC_List_GetListStartNode(&phXCOS->TimeOverflowList)) != &phXCOS->TimeOverflowList) { // 溢出表有节点
340          Tick = XC_LIST_TO_TCB(pHead)->TaskWakeupTick - Tick; // 模块差(未回绕) = 距回绕 + 唤醒时刻
341      }
342      else {          // 时间表,溢出表都没有节点;
343          Tick = ~0U; // 按最大时间休眠
344      }
345      if(XC_List_ListValid(&phXCOS->ReadyList)) { // [A17] 计算期间有任务被唤醒 ⇒ 同理不发休眠提示
346          Tick = 0U;
347      }
348      phXCOS->fIdle(phXCOS, Tick); // 框架空闲处理
```

**关键点 1："捕获节点指针再取值"直接取代加锁（隐患②的根治）**

| 步骤 | 原代码 | A′ |
| --- | --- | --- |
| 判有效 | `XC_List_ListValid(&TimeList)`（读表根 `pNext`） | `(pHead = 表根.pNext) != &TimeList` —— **同一个判断**，只是把节点指针**存进局部变量** |
| 取值 | **再读一次** `表根.pNext`，再 `container_of` 取 `TaskWakeupTick` | 对**已捕获的** `pHead`（一个真实 TCB 指针）取值 |
| 若此刻中断把节点搬走 | 第二次读可能读到**表根** ⇒ `container_of` 得到框架实例内部字节（`BlockedList.pPrev`）⇒ 垃圾值 | `pHead` 指向的 TCB 是**用户静态对象、永不释放** ⇒ 读到的永远是该任务真实的 `TaskWakeupTick` |

⇒ "把表根当 TCB 读"在**结构上不可能发生**：不依赖"此刻有没有持锁"，也不受中断是否走"直接搬表"路径的影响 ✅

**关键点 2：末尾"就绪表复检"**：把"计算期间有任务被唤醒"这一步也压成 `0`（保守：不休眠）——
它同时覆盖了"中断把时间表首节点搬到就绪表 ⇒ 手里那个 `Next` 已过时"的残余情形，代价仅 **1 次比较**。

**关键点 3：为什么溢出表分支保留"模块差"（不加 `Next > Tick` 钳位）**：
溢出表承接的是"唤醒时刻落在**下一个回绕之后**"的任务，其 `TaskWakeupTick` 的数值**天然小于**当前 Tick（如 `Next=100`、`Tick=4294967246`），
`100 − 4294967246` 按 `uint32` 取模 = **150**，正是"距回绕 50 + 回绕后 100"的正确值 ✅。
若在此分支同样加 `Next > Tick` 判断，会把正常情形误判成"已过点"⇒ 破坏既有正确行为。
真正的"已过点"情形（回绕已发生但溢出表未换表）由前面的 `PrevTick > Tick` 分支拦下 ⇒ 该分支到达时必然"未回绕"。

### 3.3 方案对照（**含实测体积**）

| 方案 | 做法 | 隐患②是否根治 | 是否动并发契约 | **实测体积**（临时打补丁实测，测完已逐字节还原） |
| --- | --- | --- | --- | --- |
| **A′（未采用；历史对照）** | **捕获节点指针**取值 + `Next > Tick` 钳位 + 就绪复检（**不加锁**） | ✅（结构上不可能读到表根） | ✅ **零变化**（不动 `Lock` 任何使用点） | `XC_Sch.o` **+20 / +16 B**（off 632→**652** / diag 708→**724**）；镜像 **+28 B**（`default` 8716→**8744**） |
| B 仅钳位 | 只把 `Next - Tick` 改成 `Next > Tick ? Next - Tick : 0U` | ❌（垃圾值 ≈5.4 亿低于任何阈值） | ✅ | （未实测，约 +8 B） |
| C 缓存 `NextWakeTick` | 在 `XCOS_t` 增字段并由改表点维护 | — | ✅ | **+4 B RAM** + 结构体变更（牵连基线/文档） |
| D 关中断 | `__disable_irq()/__enable_irq()` 包临界区 | — | ❌（违反"不关中断"设计） | — |
| E 只写文档 | 不改代码 | ❌ | ✅ | 0 |

> **为何不加锁**（**已被 2026-09-16 决策推翻**：改为"锁内取值"，见文首「实施变更」；下面的对照数据仍有效）：
> 若把"读 Tick + 判表 + 取首节点"包进 `XC_Core_Lock/Unlock`，
> 除镜像多约 **40 B** 外，还会让该窗口内到达的中断把 `SendNotify` **退化为"只登记"**（并发契约多一个使用点 + ISR 侧延迟特性改变）；
> 而"捕获节点指针"这一写法已在**结构上**排除"把表根当 TCB 读"⇒ **不需要锁**，故采用 A′。
> A′ 已用 §5.1 的复现用例验证：**修复后 `ALL PASS`**（`采样2` 由 `0xFFFFFFFF` 变为 `0`）。

> 上表中 **B / C / D / E** 的"不采用原因"展开：
> - **B**：阈值法拦不住隐患② —— `BlockedList.pPrev` 的值 ≈ `0x2000_xxxx`（5.4 亿），**低于任何"看起来可疑"的阈值**，伪装性极强；
> - **C**：需在所有改表点（入表 / 换表 / 唤醒 / 复位）同步维护，**漏一处即长期错误**＋ +4 B RAM ＋ 结构体变更（牵连 `sizeof_xcos` 基线与文档）；
> - **D**：违反"**不关中断、不依赖编译器/平台特性**"的既有设计（见 `XC_Core.h` 契约与 MISRA Deviation），且拉长中断延迟；
> - **E**：框架契约（`XC_TypeInternal.h` 的 `fIdle` 注释）要求用户"按 `IdleTick` 配置唤醒源 / 回填 Tick"⇒ 错值会被用户代码放大成实际故障。

### 3.4 并发契约的影响（A′：**零变化**）

| 项 | 说明 |
| --- | --- |
| **`Lock` 使用点** | **不新增**（`XC_Core.h` 的使用点清单不变）⇒ 不存在"新增 `Lock` 忘了 `Unlock`"这一类风险 |
| **ISR 侧代价** | **无**：不新增持锁窗口，`XC_Task_SendNotify` 的直接唤醒路径与改动前完全一致 |
| **残余竞态（如实记录）** | 中断若恰在"读 Tick / 取首节点"的几条指令之间把节点搬到就绪表：A′ **仍不会读到表根**（读的是真实 TCB 字段），只是手里的 `Next` 可能"晚了几纳秒" ⇒ 由末尾**就绪表复检**压成 `0`；最坏退化为"空闲回调被多调用一次（提示值略偏大）"，与既有"第 314 行就绪表判断同样是快照"同源 |
| **热点路径** | **无影响**：就绪表非空时不进本分支；入表 / 延时 / 通知路径一行未动 |
| **快照语义** | 空闲回调本身是"**快照**"：调用瞬间无任务就绪，下一纳秒可能有 —— 属既有契约（`XC_TypeInternal.h` 的 `fIdle` 注释）；A′ 只把窗口收窄，并且不再产生越界值/垃圾值 |

### 5.5 高频档仿真观察（MDK/µVision 模拟器，**100 kHz**）—— ✅ **已实测（before / after）**

**做法**：用 **MDK/µVision 内置模拟器**（`SARMCM3`，armcc **AC5 V5.06u7 / -O1**，Cortex-M3）**真跑调度器**，并把时基配成 **100 kHz**
（`XC_CFG_TICKS_PER_SEC=100000U`，即 72 MHz 下 720 周期/tick）；Tick 源切"**计数器模式**"由测点脚本化推进（`-ConfigTickSource`），
在"**空闲分支那次读 Tick**"上定点 `+2` —— 等价于"`TimeSched` 读完 Tick 后、空闲分支读 Tick 之前又过了 2 个 tick"（§2.1 的触发条件）。
> 说明：µVision 仿真**无外设模型**（技能文档 trap #15）⇒ 不能靠 `SysTick` 中断注入，故用"计数器模式 + 定点注入"；测点**不依赖任何外设**。

```powershell
    -ProjectDefine "XC_CFG_TICKS_PER_SEC=100000U" -ConfigTickSource "XC_SimTickRead"
```
