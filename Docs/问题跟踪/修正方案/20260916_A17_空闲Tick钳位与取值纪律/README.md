> **一句话**：调度器空闲时交给用户回调的 `IdleTick`（"建议休眠上限"）不会再出现 `0xFFFFFFFF`（≈49.7 天）或 `≈0x2000_xxxx`（表根被当任务读出的垃圾值）。

## 做了什么

只改**空闲分支**（任务切换 / 入表 / 通知三条热路径一行未改）：

| # | 改动 | 解决的问题 |
| --- | --- | --- |
| 1 | **锁内取值**：`XC_Core_Lock` 只包住"就绪表判空 + 取时间表/溢出表首节点唤醒时刻"（`fIdle` 与其余计算在锁外） | ②陈旧快照：原写法在**锁外**两次读表根（`ListValid` → 再经宏取一次），中间被中断搬空就会把**表根当 TCB** 读 ⇒ 垃圾 Tick；锁内表不会被中断改动 ⇒ 读到的是真实 TCB 字段 |
| 2 | `Next > Tick ? Next - Tick : 0U`（**已过点 ⇒ 0**） | ①下溢：负值按 `uint32` 回绕成 `0xFFFFFFFF`（≈49.7 天）交给 `fIdle` |
| 3 | `phXCOS->PrevTick > Tick` ⇒ **0** | ③窗口内 Tick 回绕（时间调度尚未换表）一样视为"已到点" |
| 4 | **锁内**再判一次就绪表 ⇒ **0** | 计算期间刚有任务被唤醒（与外层锁外快判是**不同时刻**的观察，故不是重复检查） |

同时把 **`IdleTick` 值域契约写进注释**（用户实现回调时**务必先判 0**）：

| 文件 | 落点 |
| --- | --- |

| `Code/Inc/XC_Sch.h` | `XC_Sch_SetIdleCallback` 用户说明（三档语义 + "不要把 0 直接交给设置休眠时长的接口"） |

## 复核结论（"同型写法"不立项）

`XC_Sch_TimeSched` 的两处"先 `ListValid`、再取表首/遍历"曾作为**同型写法**提出；经复核**判定非缺陷**：

- 该函数**全程持锁**（两个分支都在 `XC_Core_Lock` / `XC_Core_Unlock` 之内），而中断侧**唯一**的改表路径
  `XC_Task_SendNotify` **先读锁**（读到 1 只登记、不动链表）⇒ **临界区内链表不会被中断改动**，
  "判空后再取值"不会读到表根；
- 因此**不加防御性写法**（原先登记的 A18 条目与其修正方案**已删除**，代码也已还原）；
- 纪律：**锁是链表访问的唯一互斥手段**，不得为"假设锁失效 / 有人忘锁"写防御性写法
  （见 `Docs/Skill/XCOS_Dev_Agent_Skill.md`）。

## 已完成：空闲分支补锁（2026-09-16）

- 原「待定」项已决策并落地：空闲分支的链表读取**并入锁域** —— `XC_Core_Lock` 只包住"就绪表判空 +
  读时间表 / 溢出表首节点唤醒时刻"（无函数调用），`XC_Time_GetTick()`、回绕判断、算术与 `fIdle` 回调都在**锁外**；
  每轮空闲的锁占用 ≈ 8 条指令，**回绕轮不进锁**；
- 因此删除了"捕获表首指针"与"末尾就绪复检"两个防御件（"锁内同一次原子观察"已覆盖它们的目的）。
