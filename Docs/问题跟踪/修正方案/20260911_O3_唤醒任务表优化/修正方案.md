# O3 优化（待唤醒任务表 / ISR 永不碰链表）实测对比与综合判断

| 项 | 内容 |
| --- | --- |
| 日期 | 2026-09-11 |
| 版本 | XCOS V2.1.0（工作区 `43f9a7f` + 2 处注释级未提交改动） |
| 目的 | 量化评估 O3（`XCOS_t` 内放"待唤醒任务表"，中断只登记、主循环落地；删锁、常态免扫描）是否值得实施 |
| 仓库改动 | **无**（原型实现与测量全在临时副本 `%TEMP%\xcos_o3\` 内完成） |

| **采纳状态（2026-09-14）** | **暂不实施（决策：整体不划算）** —— 保留为数据来源与将来重开入口（禁止直接套用原型补丁） |

## 1. 你的理解确认

> "在 XCOS 句柄里放一个表存放需要唤醒的通知，元素是 `XC_TaskCB_t*`，数量可配置" —— **完全正确**，并补三点精确化：

1. **表在 `XCOS_t` 中**（不是全局）：一个工程有 M 个 XCOS 实例，就是 **M × 容量 × 4Byte** 的 RAM 开销；
2. **容量编译期可配置**：新增 `XC_CFG_WAKE_QUEUE`（建议 2~8，默认取 4）；也可用命令行 `-DXC_CFG_WAKE_QUEUE=n` 覆盖；
3. **必须是环形（头/尾索引）+ 溢出兜底**：否则中断侧无法在"不读改写、不关中断"的前提下安全入表；表满时置 `PendScan`，由主循环回退"整表扫描"保证不丢唤醒。

## 3. O3 原型的关键实现点（副本内）

| 位置 | 改动 |
| --- | --- |

| 未做 | 中断侧挂起/恢复（`PendAction` 预留位未启用）、文档/示例/测试同步、返回值文档更新 |

## 6. 运行性能（静态指令数 + Cortex-M3 周期估算）

> 说明：本机无宿主编译器/硬件，**未上板实测运行时间**；下表为 `-O2` 反汇编的**指令条数**（精确）与**周期估算**（Cortex-M3 经验模型：ALU 1、load 2、store 1、条件跳转不跳 1/跳 3、`bl/bx` 4，估算误差约 ±20%）。

### 6.1 逐函数指令数（`-O2 -S` 计数）

| 函数 | before | after | Δ |
| --- | --- | --- | --- |
| `XC_Task_SendNotify` | 58 | **28** | **-30** |
| `XC_Task_HandleWaitNotify` | 68 | 56 | -12 |
| `XC_Task_HandleSuspend` | 14 | 6 | -8 |
| `XC_Task_Suspend` | 26 | 19 | -7 |
| `XC_Task_HandleRemove` | 28 | 22 | -6 |
| `XC_Task_HandleReset` | 25 | 20 | -5 |
| `XC_Task_Resume` | 18 | 15 | -3 |
| `XC_Sch_WakePush` | — | 14 | +14（新增） |
| `XC_Sch_Start`（主循环，含内联） | 209 | 239 | +30 |

> `XC_Task_Suspend/Resume/HandleSuspend/HandleReset/HandleRemove` 的 -3~-8 条正是**锁的 store 对**被删除的效果（每个锁对约 3 条指令）。

### 6.2 主循环每轮成本（关键对比）

| 场景 | before | after |
| --- | --- | --- |
| 常态（无待处理项） | **4~5 条**：`Trigger=EventProduced; if(Trigger!=EventConsumed)`（ldrb/ldrb/cmp/beq） | **7 条**：`PendScan` 判定 3 条 + 环空判定 4 条（ldrb/ldrb/cmp/bne-not-taken） |
| "中断命中临界区"的那一轮 | **4 + 6×N**（三表扫描；实测**每节点 6 条指令**） | **7 + ≈31×K**（K=本轮待处理项数，含 `MoveNodeAfter` 调用 8 条） |

> N = 时间表 + 溢出表 + 阻塞表 内的任务总数；K = 本轮被登记的任务数（通常 1）。

### 6.3 "命中轮"收益随 N 变化（K=1，周期按每节点约 10 周期估算）

| N（表内任务数） | before（指令/轮） | after（指令/轮） | 省（指令） | 省（周期，估） | 折合时间 @72MHz |
| --- | --- | --- | --- | --- | --- |
| 10 | ~64 | ~38 | ~26 | ~50 | ~0.7 µs |
| 50 | ~304 | ~38 | ~266 | ~460 | ~6.4 µs |
| 100 | ~604 | ~38 | ~566 | ~1000 | ~13.9 µs |

> 重要前提：before 的扫描**只在"该轮有中断命中临界区"时才执行**（`EventProduced != EventConsumed`）；因此这是**命中轮**的收益，不是每轮收益。命中率为 0 时，两版常态成本相当（≈5 vs ≈7 条指令）。

### 6.4 ISR 内部最坏路径："通知一个正在等待通知的任务"

| 项 | before | after |
| --- | --- | --- |
| 指令数 | `Lock==0` 直接路径：26 + `MoveNodeAfter` 8 = **34**<br>`Lock==1` 异步路径：**≈32** | 20 + `WakePush`(14) = **34**<br>（把 `WakePush` 内联/宏化 ⇒ **≈22**） |
| 共享内存写次数 | **9**：`pNotifyData`、`Lock=1`、4 次链表指针、`Lock=0`、`NotifyState`、`TaskState` | **4**：`pNotifyData`、`NotifyPending`、环槽、`WakeTail` |
| 是否触碰链表 | `Lock==0` 触碰（4 次指针写）/ `Lock==1` 不触碰但引入后续 O(N) 扫描 | **从不触碰** |
| 路径是否恒定 | 否（两条路径长度不同） | **是**（表满兜底仅 +3 条指令） |

**结论**：ISR 指令数"持平"，但**性质改变**——不碰链表、不写锁、路径恒定；且"命中锁窗口"不再引发后续 O(N) 扫描。

## 7. 综合判断

### 7.1 一页量化总表

| 维度 | 变化 | 判定 |
| --- | --- | --- |
| **Flash（链接后）** | **-180 B（-15.4%）** | ✅ 变小（删满判定/锁/事件计数，净额大于新增的环+drain） |
| **Flash（对象级合计）** | **-218 B** | ✅ 变小 |
| **RAM / TCB** | **+0 B**（44 → 44） | ✅ 无代价 |
| **RAM / 句柄** | **+4×K B / 实例**（K=4 → +16 B） | ⚠️ 多实例线性叠加（10 实例 +160 B） |
| **主循环常态** | 5 → 7 条指令/轮 | ⚠️ 略微增加（+2 条，≈2 周期） |
| **主循环"命中轮"** | 4+6N → 7+31K | ✅ N=50/K=1 时省 ≈266 条（≈6.4 µs @72MHz） |
| **ISR 路径** | 34 → 34 条（内联后 ≈22） | ⚪ 持平；内存写 9 → 4，**不碰链表、路径恒定** |
| **确定性/可预测性** | 两条不等长路径 → 单一路径 | ✅ 显著改善（抖动） |
| **架构简化** | 删锁（13 对 + 2 单点 + 1 字节）+ 删事件计数 | ✅ 少一类竞态与推理负担 |
| **已知缺陷** | DEF-20260824-02 结构性消失（唤醒单点落地 + 显式排除挂起） | ✅ |
| **中断能力** | 为"中断里挂起/恢复"提供统一底座（TCB +0B 预留 `PendAction`） | ✅ |
| **兼容性** | 任务上下文行为不变；`WAIT` 场景返回值 `XC_CONTINUE→XC_OK`（仅原 `Lock==1` 分支） | ⚠️ 需文档/迁移说明 |
| **约束** | 通知生产中断不得相互嵌套（或改用"每生产者独占槽"变体） | ⚠️ 新增一条使用约定 |
| **改动面** | 内核 6 文件 + 文档/示例/测试（含"模拟锁窗口"用例改写） | ⚠️ 工作量集中在验证 |

### 7.2 收益换算：命中率决定一切

"命中轮"收益（N=50 时约 6.4 µs/轮）折算成 CPU 占用：

| 中断命中临界区的频率 | 每秒省时 | 占 CPU（@72MHz 满速） |
| --- | --- | --- |
| 100 次/秒 | 0.64 ms/s | **0.06%** |
| 1,000 次/秒 | 6.4 ms/s | **0.64%** |
| 10,000 次/秒 | 64 ms/s | **6.4%** |

> N=100 时上表数值翻倍（约 13.9 µs/轮）；K 增大时 after 侧按 ≈31 条/项 增加。

### 7.3 决策建议

| 你的目标 | 建议 | 理由 |
| --- | --- | --- |
| **① 想让中断里能挂起/恢复任务** | ✅ **做**（O3 是唯一优雅底座） | `PendAction` 复用 TCB 对齐 padding（**+0B**），与唤醒走同一张表；不必再引入第二套机制 |
| **② 想修 DEF-20260824-02（挂起任务被误唤醒）** | ✅ **做**（或先只做两处小改） | O3 后唤醒只有"主循环单点落地"一条路径，且显式排除 `SUSPEND`，缺陷类别消失 |
| **③ 纯为性能** | ⚠️ **先埋点实测命中率**，命中率 < 数千次/秒则**不值得** | 0.06%~0.64% CPU 的收益不足以承担语义/文档/测试改动风险 |
| **④ 系统 N 大（表内任务 ≥50）且 ISR 密集（≥1kHz 且多通知源）** | ✅ 收益显著（可达数 % CPU） | 命中轮收益随 N 线性增长，而 after 侧与 N 无关 |
| **⑤ 想要"少一套 API / 省资源"** | ⚠️ 资源上是净赚（Flash -180B、RAM +16B/实例），但语义上不建议把"挂起"降级为"等待通知" | 见前几轮结论：level 状态 vs edge 事件不可互换 |

**一句话**：O3 **不是纯性能优化**，而是一次"**Flash 略降 + 每实例 +4K 字节 RAM + 最坏路径确定化 + 语义修复 + 为中断侧挂起/恢复铺路**"的架构级重构；**该不该做取决于 7.3 的 ①②④ 是否命中你的需求**，而不是取决于那点扫描开销。

### 7.4 若实施：建议分阶段（每阶段可独立回归/回退）

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| **P0** | 埋点 3 个计数（直接路径命中 / 锁窗口命中 / 扫描节点数），实测命中率 | 得到 7.2 表中你的实际工作点 |
| **P1** | 引入 `WakeQueue` + `WakePush` + `WakeSched`；`SendNotify` 改为"只登记"；**保留锁与兜底扫描** | 通知/挂起/延时全量回归；扫描次数≈0 |
| **P2** | 删 `EventProduced/EventConsumed` 与常态扫描；计数对→`NotifyPending` | 环满兜底用例（K+1 个不同目标一次性唤醒） |
| **P3** | 删 `Lock`、13 对 Lock/Unlock、`XC_Core_GetLockState`、`XC_Sch_Init` 的锁初始化；同步文档/示例/测试 | 全量回归 + MISRA 复核；预计再省 15~30 B |
| **P4** | `PendAction` 并入同表 ⇒ 中断侧挂起/恢复 | 新增中断挂起用例；DEF 用例变为"必须通过" |

### 7.5 必须守住的不变量与风险清单

**不变量**（与现状一致，O3 不改）：
1. 等待通知 = 让出点（`XC_Cor_WaitNotify` 必 `COR_SetBPBreak`）；
2. `HandleWaitNotify` "先置 `WAIT`、再查 pending"（防丢唤醒的唯一依赖）；
3. 非抢占、单任务单表、表尾轮转 + 唤醒插队首；
4. **ISR 只登记**（O3 的立足点，后续新增中断 API 必须遵守）。

**风险与对策**：
| # | 风险 | 对策 |
| --- | --- | --- |
| 1 | `WAIT` 场景返回值由 `XC_CONTINUE`→`XC_OK` | CHANGELOG/API 文档显式说明；或统一为"ISR 恒 `XC_CONTINUE`、任务上下文恒 `XC_OK`"二选一 |
| 2 | 共享环要求生产者不嵌套 | 文档约束；或"每生产者独占槽"变体（`N×4B`，无头尾索引，天然嵌套安全） |
| 3 | 环满 ⇒ 兜底扫描 | 保留 `XC_WakeScan`（原 `WAKEUP_NOTIFY`）作为稀有路径，并覆盖测试 |
| 4 | 唤醒顺序（环 FIFO + 表首插入 ⇒ 最后登记先运行） | 需要"先登记先运行"则反向落地；写入文档 |
| 5 | 多实例 RAM 线性叠加 | 按 `XC_CFG_WAKE_QUEUE` 选型（K=2 时仅 +8B/实例） |
| 6 | 旧测试用例"模拟锁窗口"失效 | 改写为"环满兜底""环内陈旧项"等用例 |

## 9. 案例研究：串口接收（32 字节/块 + 3 字节空闲触发超时，中断中通知一次）

### 9.0 符号说明（先看这里）

| 符号 | 含义 | 怎么取值 | 本场景典型值 |
| --- | --- | --- | --- |
| **N** | **当前躺在"时间表 + 时间溢出表 + 阻塞表"里的任务数**（= 整表扫描会扫到的节点数）。**不含**正在运行的任务和就绪表里的任务 | 按任务状态统计，或在扫描循环里累加计数 | **≈15~20** |
| **p** | **中断里调用 `SendNotify` 时，恰好主循环正持锁（`Lock==1`）的比例**（= 锁的占空比，0~100%） | 加 2 个计数器：`SendNotify` 总次数、命中 `Lock==1` 分支次数；p = 后者 ÷ 前者 | **≈5%~15%** |
| 6 | 现状"整表扫描"每扫描**一个节点**的指令数（实测，`-O2`/Cortex-M3） | 反汇编计数 | 6 条/节点 |
| 10 | 扫描的固定开销（建循环、起始判断、函数收尾等） | 同上 | ≈10 条 |
| 31 | O3 每次通知在**主循环排空一项**的指令数（实测） | 同上 | 31 条 |
| 34 | 两种设计在 **ISR 内**的指令数（现状 `Lock==0` 直接搬表 / O3 登记入环） | 同上 | 34 条（O3 内联 `WakePush` 后 ≈22） |

**为什么"看这两个参数就够了"**：

```c
现状 SendNotify:
  Lock==0(概率 1-p) -> 中断自己 O(1) 搬表            : 34 条, 不产生扫描
  Lock==1(概率 p)   -> 只记计数, 下一轮主循环整表扫描 : 34 条 + (6N+10) 条
  ⇒ 每次通知平均: 34 + p×(6N+10)

O3 SendNotify:
  恒定 -> ISR 登记入环(34) + 主循环排空一项(31)      : 65 条
```

**每次通知的净差（正 = O3 更贵）**：

```
Δ = 31 − p × (6N + 10)        盈亏平衡:  p* = 31/(6N+10)
```

* `p*` 只与 **N** 有关（N=15→29.2%、N=20→23.8%、N=25→19.4%），**与波特率无关**——波特率只决定"收益/成本的绝对值"（同比例放大），不决定"该不该做"。
* 也就是说：**p 越大 / N 越大 ⇒ O3 越划算**；反之就是白付那 31 条排空指令。

**怎么在自己工程里量**：

1. **N**：在扫描循环（`WAKEUP_NOTIFY` 的 `do{}while`）里，每访问一个节点 `g_ScanNodeCnt++`；或遍历 TCB 用 `XC_Task_GetState()` 统计 `BLOCKED`/延时中的任务数。
2. **p**：在 `XC_Task_SendNotify` 里加两个 `volatile uint32_t`：进入函数 `g_SnTotal++`；走到 `Lock==1`（异步）分支时 `g_SnAsync++`。跑真实负载后 `p = g_SnAsync / g_SnTotal`。
3. 这两个计数就是第 7.4 节的 **P0 埋点**；拿到之后套 `Δ = 31 − p×(6N+10)` 即可判定 O3 对你是赚还是赔。



* 串口格式 **8N1 ⇒ 10 bit/字节**；
* 发送端节奏：**32 数据字节 + 3 字节空闲** = **35 字节时间/块**，接收侧每块产生 **1 次接收超时中断**，中断中 **发 1 次通知**；
* 通知频率 = 波特率 ÷ 350。

| 波特率 | 1 字节时间 | 1 块周期 | **通知频率** |
| --- | --- | --- | --- |
| 115200 bps | 86.8 µs | 3.04 ms | **329 次/秒** |
| 1 Mbps | 10 µs | 350 µs | **2,857 次/秒** |
| 2 Mbps | 5 µs | 175 µs | **5,714 次/秒** |

### 9.2 每次通知的框架成本（用第 6 章的实测指令数）

| 路径 | 现状（before） | O3（after） |
| --- | --- | --- |
| ISR 内 | 34 条（`Lock==0` 直接搬表）；`Lock==1` 时 32 条，但**触发后续整表扫描** | 34 条（`WakePush` 内联后 ≈22 条） |
| 主循环内 | 仅在"命中临界区"时：`6×N + ~10`（N=三表内任务数）；未命中为 0 | **每次通知都要排空**：≈31 条/项 |

**每次通知的净差**（正 = O3 更贵）：

```
Δ = +31 − p × (6N + 10)          p = 中断命中临界区的比例
盈亏平衡:  p* = 31 / (6N + 10)
```

| N（三表内任务数） | 5 | 10 | 20 | 50 |
| --- | --- | --- | --- | --- |
| 回本所需命中率 p* | **78%** | **44%** | **24%** | **10%** |

> XCOS 的临界区都很短（取任务/归位、时间表插入、扫描），**实际 p 通常只有 1%~5%** ⇒ 达不到 p*。

| 情形 | Δ/次通知 | 115200 | 1 Mbps | 2 Mbps |
| --- | --- | --- | --- | --- |
| **典型：p=3%、N=10** | **+29 条（O3 多花 0.52 µs）** | **−0.017% CPU** | **−0.15%** | **−0.30%** |
| 极端：p=100%、N=10 | −39 条（省 0.70 µs） | +0.023% | +0.20% | +0.40% |
| 极端：p=100%、N=50 | −279 条（省 5.04 µs） | +0.17% | +1.44% | **+2.88%** |

（正 = 省 CPU，负 = 多花 CPU）

### 9.4 对照：整个通知机制本身的开销

| 版本 | 每次通知 | 2 Mbps 下占用 CPU |
| --- | --- | --- |
| 现状 | 34 条 ≈ 0.61 µs | 3.5 ms/s ≈ **0.35%** |
| O3 | 65 条 ≈ 1.17 µs | 6.7 ms/s ≈ **0.67%** |

**即：本场景下连"整套通知机制"也只占 0.35%~0.67% CPU**，可优化空间本来就很小。

### 9.5 结论（本案例）

1. **性能收益 ≈ 0**：典型参数下 O3 反而**多花 0.02%~0.3% CPU**；只有在"每次通知都命中临界区 + N≥50"的极端假设下才省 **0.17%~2.88%**。
2. **"是否值得"与波特率无关**：成本与收益都随通知频率线性缩放，判据只取决于 `p` 与 `N` 的比较（p 需 ≥10%~44% 才回本），而实际 p≈1%~5% ⇒ **为性能做 O3 不划算**。
3. **通知粒度决定量级**：若改成"每字节通知一次"（本场景 ×32），2 Mbps 下现状约 **11%~15% CPU**、O3 约 **22%~30% CPU** —— 此时正确做法是 **DMA + 块中断**（减少通知次数），而不是 O3。
4. 因此：**本场景若要动 O3，应是为"架构收益"**（中断侧挂起/恢复、DEF-20260824-02 修复、ISR 路径恒定/可预测），**不是为性能**。

### 9.6 本场景真正值得优化的点（收益远大于 O3）

| # | 优化 | 量化依据 |
| --- | --- | --- |
| 1 | **DMA + IDLE(接收超时)/TC 中断**，避免逐字节 RX 中断 | 2 Mbps 逐字节 = 183k 中断/秒；HAL 层层调用下可达 **数十 % CPU** |
| 2 | **缓冲深度按最坏唤醒延迟设计** | 2 Mbps = 200 kB/s；最坏唤醒延迟 1 ms ⇒ 需 ≥200 B（≈7 块） |
| 3 | **通知带数据指针**（`pNotifyData` 传 DMA 块地址）+ 双缓冲/环形缓冲 | 免二次拷贝，省 32 B/块的 memcpy 与延迟 |
| 4 | **单生产者纪律** | 一个任务只由一路中断通知；否则违反 SPSC（多生产者需用户加锁） |
| 5 | **任务处理预算** | 2 Mbps 每 175 µs 一块，处理需在块周期内完成，避免积压 |

**重要前提与加固点**：O3 的"空环检查"是**每轮固定成本**。实测口径 61 周期含（测点挂钩的两层函数调用 + 12 周期计时开销），主循环内联后更低；但若主循环轮次率**远高于**通知率（例如 50k 轮/秒 vs 20k 通知/秒），固定成本会按轮次率线性放大（50k × 61 ≈ 3.05M 周期/秒 ≈ **4.2% CPU** @72MHz）。加固办法：把 `PendScan` 与"环非空"合并为**一次字节读 + 早退**，或把排空做成"有登记才调用"。

### 10.5 实测结论

1. **收益真实存在但只在"命中率够高"时成立**：命中轮省 **239 周期/次**（−64%），平衡点是 **q\*≈16%**；你的场景 p≈5%~15% ⇒ **打平附近、偏亏 0.1%~1.1% CPU（4×2 Mbps）**。
2. **p 超过 ~25% 后才明显赚**（0.8%~8%，随波特率与 p 放大）。
3. **资源侧实测**：Flash **−72B（AC5 -O1）/ −180B（AC6 -O2）**，RAM **+16B/实例**（K=4）。
4. **ISR 侧确实变短**（110→95；Suspend/Resume −10），这对"中断响应确定性/抖动"是正面收益（与 CPU 收益无关）。
5. 与第 7/9 章的估算结论一致，但现在有实测支撑：**为性能做 O3，只有当你系统里"锁命中率 ≥ ~16%~25%"时才划算；否则它的价值在架构（中断侧挂起/恢复、DEF-20260824-02 修复、ISR 路径确定）。**

### 10.6 "每轮固定税"的优化与复测（单标志门控）→ **结论反转**

#### 做法（安全实现）

新增 **1 字节 `WakePending`**，规则：**中断只写 `1`、主循环处理前写 `0`**（两边都只写常量 ⇒ **不存在读改写**，多中断源也安全）：

```c
/* 中断侧(登记) */  phXCOS->WakePending = 1U;            /* 成功/失败都置; 失败另置 PendScan 兜底 */
/* 主循环(门控) */  if(phXCOS->WakePending == 0U) { return; }   /* 1 次字节读 + 分支 */
                    phXCOS->WakePending = 0U;                   /* ★ 先清后处理: 处理期间中断再置位 => 下轮再来, 不丢 */
                    ...排空环 / 若 PendScan 则整表扫描...
```

> ⚠️ **不能**用"中断与主循环共享一个 `++/--` 计数"：ISR 的自增与主循环的自减会互相覆盖（无保护读改写）⇒ 计数可能提前归零 ⇒ **丢唤醒**。这正是 XCOS 当初用"生产/消费双计数"的原因；单标志方案规避了它（因为两边都只写常量）。

### 10.8 更正-2（最终）：登记改宏后的复测 —— `SendNotify` 确实很便宜，但"通知→落地"总账仍偏贵

反馈"O3 的 `XC_Task_SendNotify` 不该那么慢"是对的：10.7 里的 **99 周期是 AC5 -O1 未内联函数调用的假象**（`SendNotify` 本身 + 它对 `XC_Sch_WakePush` 的调用，两层都不内联）。把登记改成**宏**（与 `XC_SCH_TAKE_FIRST`/`XC_SCH_PUT_TAIL` 同风格）后复测：

| 测点 | 现状 | O3（登记=函数） | **O3（登记=宏）** |
| --- | --- | --- | --- |
| `SendNotify`（目标在等待） | 110 | 99 | **78** |
| `SendNotify`（目标非等待） | 63 | 54 | **51** |
| 主循环落地 1 项（增量） | 0（落地含在发送里） | 96 | 96 |
| 每轮门控 | 13 | 9 | 9 |
| **"通知→落地"总计（同口径 r16）** | **110** | — | **208**（含测试钩子 2 层调用；主循环内联后约 183） |
| `Code`（两版测点等长） | 2116 | — | **2048（−68）** |
| `ZI` / `sizeof(XCOS_t)` | 2388 / 44 | — | 2404 / 64（+20/实例） |
| `Suspend` / `Resume` | 104 / 85 | — | 94 / 75 |

#### 为什么总账仍偏贵（即便 `SendNotify` 只要 78）

* 现状是"**在调用者上下文一次做完**"：110 里已含 `XC_List_MoveNodeAfter`（实测 46）与状态写入；
* O3 要**第二次进主循环**做落地：取环项 + 索引维护 + 4 项有效性复检 + 又一次 `XC_List_MoveNodeAfter`（46）⇒ 增量 **96**；
* 即：**"搬表"两边都要付（46）**，O3 多出来的是"**环的往返 + 有效性复检**"，约 **60 周期**。

#### 修正后的模型（每次通知，R≈1）

```
现状 = 123 + 353p
O3   = 183                 (78 登记 + 96 落地 + 9 门控)
Δ(正 = O3 更贵) = 60 − 353p          ⇒  平衡命中率 p* ≈ 17%
```

#### 最终结论（经三次更正）

1. **`SendNotify` 在 O3 里很便宜**（宏版 78，纯登记约 66）——你的直觉对；10.7 的 99 是 -O1 未内联的假象。
2. 但 **"通知→落地"的总账在 p≈2% 下仍偏贵**：每次约 +53~60 周期 ⇒ **−1.7% CPU @4×2 Mbps**，平衡点 **p\* ≈ 17%**。
3. 根因是"**环的往返 + 把落地搬去主循环**"，与 `SendNotify` 本身的快慢无关。
4. 所以：**性能上不做 O3；架构上可做**（ISR 不碰链表/无锁、ISR 路径恒定、修 DEF-20260824-02、支持中断侧挂起/恢复）。
### 10.9 怎么优化才能"中断唤醒与任务唤醒都要收益"

#### 先看实测出来的成本结构（AC5 -O1，21 节点；已把 `MoveToReadyList` 宏化）

| 项 | 现状（含落地宏化） | O3（含落地宏化） | 说明 |
| --- | --- | --- | --- |
| `SendNotify`（目标在等待，未持锁） | **104** | **78** | 现状含落地；O3 只登记 |
| `SendNotify`（目标非等待） | 61 | 51 | — |
| 落地 `MoveToReadyList`（宏化后） | **42** | 42 | 两边共享；宏化收益 −4 |
| 主循环落地 1 项（增量） | 0（含在发送里） | **92** | 环往返 + 复检 + 落地 |
| 每轮门控 | 13 | 9 | — |
| **"通知→落地"总成本** | **104** | **179~204** | 差 ≈ +55~60 |
| `HandleDelay` 锁内插入（20 节点） | 335 | 325 | **全场景公共开销** |
| `Code` / `ZI` / `sizeof(XCOS_t)` | 2256 / 2388 / 44 | 2188 / 2404 / 64 | Flash −68、RAM +20/实例 |

**成本结构结论**：真正的"大头"是 ①`HandleDelay` 的锁内 O(M) 插入（335 周期/次，25 任务场景 ≈10% CPU）；②落地搬表（42）；③O3 多出的"环往返+复检"（≈55~60）。

#### 三条路线（可组合）

**方案 A（零回归，小收益）：O3-lite —— 只把"命中锁窗口"的延迟路径换成环**
* 保留现状全部主路径：任务侧与 ISR 侧在 `Lock==0` 时**仍直接落地（104，不变）**；
* 仅把 `Lock==1` 的延迟路径从"计数 + 下一轮 O(N) 扫描（373）"换成"环 + 下一轮 O(K) 落地（92+9）"；
* 效果：那 2% 的通知从 `88+373=461` → `88+92+9=189`，**每次省 272 周期**；平均 **+5 周期/次 ≈ +0.17% CPU（4×2 Mbps）**；
* 代价：保留 `Lock` 与"ISR 碰链表"，**拿不到**去锁/中断侧挂起恢复的架构收益；改动最小、风险最低。

**方案 B（要架构、又要两边赚）：O3 全量 + 上下文分流 + 两侧做薄**
| 步骤 | 内容 | 实测/预计 |
| --- | --- | --- |
| 1 | **上下文分流**：任务上下文直接落地；中断上下文入环 | 任务侧回到 **104**（不再付 55~60） |
| 2 | **ISR 侧登记极简化**（状态判定合并成位掩码、宏化入环、去掉冗余检查） | 78 → **≈45~50** |
| 3 | **主循环落地做薄**（`volatile` 读本地缓存、状态判定一次完成、门控与索引合一） | 92 → **≈60~70** |
| 4 | **落地宏化**（已做） | 两边各省 4~6 |
| 5 | 门控合一（单标志） | 13 → **9** |
| **结果** | 任务侧 ≈104（持平/略优）；ISR 侧 ≈45+65+9 = **119** vs 现状 117（**基本持平**） | 且获得：去锁、ISR 不碰链表、ISR 路径恒定、中断侧挂起/恢复、修 DEF-20260824-02 |

> 方案 B 的关键前提是**上下文判定**：`__get_IPSR()`（Cortex-M，1 条 `MRS`，与"纯 C"定位冲突，可做成可选宏）**或**拆 API（`...SendNotify()` / `...SendNotifyIsr()`，保持纯 C 但需用户选对）。

**方案 C（性能大头，与唤醒路径无关）：把时间表插入做薄**
* `HandleDelay` 锁内 O(M) 有序插入 = **335 周期/次**；本场景让出 ≈22,857 次/秒 ⇒ **≈10.6% CPU @72MHz**；
* 手段：分桶/时间轮（插入 O(1)）、"锁外乐观遍历 + 锁内校验插入"、按唤醒时刻分档；
* 收益量级 **是 O3 的 10 倍以上**，且**顺带把 p 压得更低**（锁窗口主要来自它）。

#### 一句话答复

* **只想两边不变慢、又拿一点收益** ⇒ **方案 A（O3-lite）**：零回归，每次命中省 272 周期（平均 +0.17% CPU @4×2 Mbps）。
* **想要架构收益、又要两边都不亏** ⇒ **方案 B**：任务侧不变（104），ISR 侧做到 ≈119（≈持平），同时去锁 + ISR 不碰链表 + 可做中断侧挂起/恢复。
* **想要真正的性能提升** ⇒ **方案 C**：先动时间表插入（335 周期/次 ≈10% CPU），收益量级远大于唤醒路径优化。

### 10.10 最终裁定：性能账上"不划算"；该动的地方在别处

| 候选改动 | 收益（4×2 Mbps、p≈2%，实测口径） | 代价 | 值不值 |
| --- | --- | --- | --- |
| **O3 全量** | **−1.7% CPU（净亏）** | RAM +20B/实例；返回值/文档/示例/测试改动面大；生产者不得嵌套的约束 | ❌ |
| **O3-lite**（只把 `Lock==1` 的延迟路径换成环） | +0.17% CPU（2% 场景每次省 272 周期） | 加环(+16B)、改内核、回归测试；拿不到架构收益 | ❌（收益 ≈ 噪声） |
| **落地宏化**（`MoveToReadyList` 内联） | +0.09% CPU | **Flash +140B**（每个调用点都展开） | ❌（拿 Flash 换 CPU） |
| **满判定回绕修复**（`(uint8_t)(Produced + 1U)`，1 字符） | 正确性：消除"累积 255 次后丢唤醒" | 0 | ✅ **唯一纯赚** |
| **时间表插入分桶 / 时间轮** | **≈ +8~9% CPU**（335 → 目标 ≤100 周期/次，22,857 次/秒） | 内核改动（中等），需回归 | ✅✅ **钱在这里** |
| 减少"让出次数"（UART 加大块长 32→128/256B） | 通知率降 4~8 倍 ⇒ 通知机制开销与线路浪费同时下降 | 协议/上位机改动 | ✅（若可协商） |

**结论**：
1. **性能上不做 O3（含 O3-lite、含落地宏化）**——在 p≈2% 的工作点上，唤醒路径没有可捞的油水（O3 净亏、O3-lite 只值 0.17%、宏化拿 Flash 换 0.09%）。
2. **唯一零成本的修复**是满判定回绕（防丢唤醒），建议单独修掉。
3. **要做性能，先做时间表插入**（收益量级是唤醒路径的 50 倍以上），并且它还会**顺带把 p 压低**，使将来真要评估 O3 时的结论更不利（进一步说明不必动 O3）。
4. **再回看 O3 的条件**：`p ≥ ~17%`（延时任务更多、锁窗口更长），**或**你需要"中断侧挂起/恢复"——那时 O3 是唯一优雅底座，+0.5~2% CPU 的成本应视为**架构投资**，而不是性能优化。






**结论**：把门控做成"单标志"后，**O3 在你这个场景里从"略亏"翻转为"净赚"**（p=5%~15% ⇒ 省 0.5%~1.2% CPU），同时 Flash −48B、ISR 路径略短（110→99；Suspend/Resume 104/85→94/75），代价是 **RAM +20B/实例**（K=4；链接器 ZI 汇总 +16，差 4B 为 `.bss` 对齐位移）。
