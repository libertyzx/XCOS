## 1. 缺陷现象

已挂起的任务（`SUSPEND`、阻塞表）被 `XC_Sch_EventSched` 的"通知唤醒"逻辑**误移入就绪表并置 `READY`**，其 WaitNotify 后续代码被继续执行，违反文档"**挂起后只能被挂起恢复唤醒**"。

## 2. 触发链（时序）

`XC_Sch_EventSched` 中 `WAKEUP_NOTIFY` 宏遍历三张表，唤醒条件为 `NotifyState==WAIT && NotifyProduced!=NotifyConsumed`：

```
1. 任务 A: XC_Cor_WaitNotify(1000) 无通知
   → BLOCKED + 时间表(NotifyState=WAIT, Produced==Consumed)

2. 中断在锁窗口(主循环 TimeSched/EventSched 期间): XC_Task_SendNotify(A)
   → SendNotify 明确支持中断; Lock==1 → 走异步分支: EventProduced++, 不移表
   → 此刻 Produced=1 != Consumed=0, 通知待消费

3. 另一任务(运行中, 任务上下文, 合法): XC_Task_Suspend(A)
   → 挂起不需要中断; TaskState=SUSPEND + 移入阻塞表
   → 挂起不清除通知: NotifyState 仍 WAIT, Produced=1 仍待消费

4. 主循环 EventSched(EventProduced != EventConsumed 触发)
   → WAKEUP_NOTIFY(阻塞表) → A: WAIT && Produced!=Consumed → 误唤醒!
   → 移就绪表 + NotifyState=WAKEUP + TaskState=READY (覆盖 SUSPEND)
```

**关键点**：`XC_Task_SendNotify` 对"**发送时已挂起**"的任务返回 `XC_FAIL`（先挂起、再通知，确实唤不醒）；本缺陷绕过它是因为**通知先于挂起发生**——挂起动作本身**不清除通知**，于是阻塞表里出现"`SUSPEND` + `WAIT` + 未消费通知"的任务，被 `EventSched` 的事件补偿误唤醒。**全程不需要中断 Suspend**（中断只做 SendNotify，Suspend 由任务上下文调用）。

## 3. 根因分析

**现行代码**（`XC_Sch.c` `WAKEUP_NOTIFY` 宏）：

```c
if((XC_LIST_TO_TCB(pIterator)->NotifyState == (uint8_t)XC_NOTIFY_WAIT) &&
   (XC_LIST_TO_TCB(pIterator)->NotifyProduced != XC_LIST_TO_TCB(pIterator)->NotifyConsumed)) {
    ...唤醒: MoveToReadyList + WAKEUP + READY...
}
```

`XC_Task_SendNotify` 的挂起保护（`TaskState==SUSPEND → XC_FAIL`）只作用于"发送侧"；`EventSched` 的事件补偿路径遍历时**只检查通知状态、未检查 `TaskState`**，绕过了发送侧的挂起保护，把"先有通知、后被挂起"的任务误唤醒。

## 4. 影响与严重程度

**中**（触发需"异步 SendNotify + 随后 Suspend + EventSched"两步外部时序，多出现在中断场景）。

- 挂起语义被破坏：任务在挂起期间被调度运行，可能执行到其 WaitNotify 之后的关键代码；
- 若任务在误唤醒后再次让出且调用 `XC_Cor_Reset`，还会清栈，挂起彻底失效。

## 5. 实测复现（gcc，当前内核未修改）

```

[Bug#2] A woke-up count = 1 (expect 0); A state = 2 (expect SUSPEND=4)

```

## 6. 修复方案（备选，已实测有效但未实施）

**改动 1**：`WAKEUP_NOTIFY` 唤醒条件追加"非挂起"判断：

```c
if((XC_LIST_TO_TCB(pIterator)->NotifyState == (uint8_t)XC_NOTIFY_WAIT) &&
   (XC_LIST_TO_TCB(pIterator)->NotifyProduced != XC_LIST_TO_TCB(pIterator)->NotifyConsumed) &&
   (XC_LIST_TO_TCB(pIterator)->TaskState != (uint8_t)XC_TASK_SUSPEND)) {   // 挂起任务不唤醒
```

**改动 2（配套，消除副作用）**：`XC_Task_Resume` 在恢复任务时补齐通知状态（锁内）：

```c
/* 挂起期间保持的"等待通知"状态补结:
 * - 有未消费通知 → 消费 + 置 WAKEUP(恢复后 IsNotifyTimeout==0, 可获取通知);
 * - 无通知       → 保持 WAIT(恢复后 IsNotifyTimeout==1, 报超时, 语义正确) */
if(phTCB->NotifyState == (uint8_t)XC_NOTIFY_WAIT) {
    if(phTCB->NotifyProduced != phTCB->NotifyConsumed) {
        phTCB->NotifyConsumed = phTCB->NotifyProduced;
        phTCB->NotifyState    = XC_NOTIFY_WAKEUP;
    }
}
```

**修复后实测**（临时副本）：

```
# 修复后内核(临时副本):
[Bug#2] A woke-up count = 0 (expect 0); A state = 4 (expect SUSPEND=4)
   └─ A 保持挂起(未被误唤醒), 状态正确报 SUSPEND(4)
```

> 改动 2 的原因：仅加改动 1 后，挂起任务保持挂起，但 `Resume` 恢复时若挂起前有未消费通知，`NotifyState` 仍为 `WAIT`，任务恢复后 `XC_Cor_IsNotifyTimeout()` 会**误报超时**（有通知却报超时）；改动 2 在 `Resume` 时补消费，保证恢复后通知状态一致。

## 7. 决策：不修复（用户决策）

- **不在框架层修复**：完整修复需配套修改 `XC_Task_Resume`（挂起恢复通知语义变更），权衡后暂缓。
- **已落地动作**：在 `XC_Sch.c` `WAKEUP_NOTIFY` 宏注释中记录为**已知缺陷（使用注意）**：

```c
 * - **已知缺陷(使用注意)**: 唤醒条件未排除挂起任务(`TaskState==SUSPEND`)——
 *    若任务在等待通知(`NotifyState==WAIT`)期间收到异步通知(中断在锁窗口
 *    SendNotify,仅 `Produced++` 未移表),随后被挂起(挂起不清除通知),本宏会在
 *    事件调度中误唤醒该挂起任务,破坏"挂起只能 Resume 恢复"语义;
 *    此路径需用户使用层面保证(勿对"等待通知中且可能收到异步通知"的任务挂起),
 *    框架暂不处理;
```

**用户使用保证约定**：不要对"处于等待通知（`XC_Cor_WaitNotify`）中、且可能收到异步通知（中断 `SendNotify`）"的任务执行挂起；若必须挂起，先 `XC_Cor_ClrNotify()` 清除通知或确认无未消费通知。
